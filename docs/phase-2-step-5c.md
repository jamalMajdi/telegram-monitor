# المرحلة الثانية — الخطوة 5 (ج): الاستخراج المقيَّد بالقرائن واكتشاف فئات التواصل

> النطاق المنفَّذ: استخراج حقول المعلومات من الرسائل **المطابقة فقط** بالاعتماد على قرائن لفظية صريحة،
> مع إسناد كل قيمة إلى موضعها في النص الأصلي (span) وحساب ثقة حتمية، واكتشاف أرقام الهواتف والمعرّفات
> والروابط وتخزينها بصيغة محجوبة جاهزة للعرض. لم يُنفَّذ بعد: التصنيف، اختيار القالب، بناء المنشور،
> والإرسال (الخطوة السادسة وما بعدها).

## 1) المبادئ المطبَّقة

1. **لا استخراج بلا قرينة.** لا تُستخرج قيمة إلا إذا سبقها لفظ دالّ من قاموس القرائن
   (`الراتب:`، `الموقع:`، `الموعد النهائي:`، `مطلوب`…). لا تخمين من كلمات عامة.
2. **لا اختراع.** `value_text` دائماً `source.slice(span_start, span_end)` حرفياً من نص الرسالة أو تعليقها،
   وهذا مُتحقَّق منه في كل اختبار. لا تلخيص ولا تصحيح إملائي ولا ترجمة.
3. **الحقل الغائب يُحذف** ولا يُملأ بقيمة افتراضية (§7.4) — لا صف = لا حقل.
4. **الغموض يُعلَن لا يُحسم.** تعدّد قيم الحقل نفسه، أو رقم تواصل قصير قد يكون معرّفاً، يُعلَّم
   `ambiguous` ويُرفع `review_state=needs_review` مع بقاء الحالة `processed` (Q7).
5. **الحجب جاهز من المصدر.** كل قيمة تواصل تُخزَّن مع `value_masked` (O03)، ولا تُعاد القيمة الخام في أي واجهة.

## 2) قاعدة البيانات — `0012_message_extraction.sql`

| الكائن | المحتوى |
| --- | --- |
| `extraction_source` | `text` / `caption` — مواضع كل قيمة تُحسب داخل مصدرها |
| `contact_kind` | `phone`, `username`, `telegram_id`, `email`, `url`, `invite_link` |
| `message_extraction` | `identity_id`, `field_key`, `value_text`, `span_start`, `span_end`, `source`, `cue`, `confidence numeric(3,2)`, `ambiguous`, `extraction_version` |
| `message_contacts` | `identity_id`, `contact_kind`, `value_raw`, `value_normalized`, `value_masked`, المواضع، `confidence`, `ambiguous`, `extraction_version` |
| `message_identity` (جديدة) | `extraction_version`, `extraction_count`, `contact_count`, `extracted_at` |
| `telegram_sources` (جديدة) | `extracted_count` (Q14) |

قيود التحقق: `span_end > span_start`، طول القيمة 1..200، `0 ≤ confidence ≤ 1`، وقائمة `field_key` المسموحة
مفروضة في قاعدة البيانات (15 حقلاً = اتحاد حقول القوالب الجاهزة في §7.2).

الحذف: الجدولان مرتبطان بالهوية بـ`on delete cascade`، ويحذفهما تنظيف الاحتفاظ أيضاً مع المحتوى
لأنها «نتائج» تُصنَّف كبيانات شخصية (Q12/O03).

## 3) الاستخراج — كيف يعمل

1. **تطبيع بخريطة فهارس** (`normalizeWithMapping`): يُنتج النص المطبَّع + مصفوفة `map` تربط كل محرف مطبَّع
   بفهرسه في النص الأصلي (طول متساوٍ، تصاعدية، تُقصّ المسافات الطرفية). هذا هو ما يجعل المواضع صحيحة
   رغم حذف التشكيل وتوحيد الأرقام.
2. **مطابقة القرائن** بحدود كلمات Unicode مع تسامح السوابق الملتصقة (نفس منطق الفلترة المعتمد)،
   والقرائن الأطول أولاً (`الموعد النهائي` قبل `الموعد`).
3. **اقتطاع القيمة من النص الأصلي** بعد القرينة: تخطّي `:`/`-`/المسافات، والتوقف عند نهاية سطر أو ترقيم
   أو 80 محرفاً، ثم قصّ المسافات الطرفية وتصحيح المواضع.
4. **رفض القيم غير الصالحة**: فارغة، أو قيمة هي قرينة حقل آخر، أو حقل رقمي بلا أرقام
   (`budget`/`area_size`/`question_count`)، أو موعد بلا دلالة زمنية.
5. **الثقة** (حتمية، بلا عشوائية):

   | المعيار | الأثر |
   | --- | --- |
   | قرينة من كلمتين أو أكثر | +0.15 (خلاف ذلك +0.05) |
   | ملاءمة نوع القيمة (رقم في حقل رقمي/دلالة تاريخية/طول 2–40) | +0.12 … +0.15 |
   | القيمة تنتهي بحدّ سطر أو ترقيم | +0.10 |
   | القرينة في بداية سطر/رسالة | +0.05 |
   | طول > 40 محرفاً | −0.10 |
   | مرشّح غير وحيد للحقل | −0.05 |

   النتيجة محصورة في `[0.25, 0.95]`؛ وأي قيمة ثقتها < 0.6 أو معلَّمة غامضة ⇒ `needs_review`.

## 4) فئات التواصل والحجب (O03)

- **الهواتف**: دولية `+967…`، محلية `077…`، جوال يمني `7XXXXXXXX`، وأرقام داخل `wa.me`؛ الأرقام
  العربية-الهندية والفارسية تُقرأ وتُطبَّع.
- **المعرّفات**: `@username`، وروابط `t.me/username`، ومعرّف رقمي بقرينة (`معرفي: 123456789`).
- **الروابط**: بريد إلكتروني، روابط عامة، وروابط دعوة تيليجرام (`t.me/+…`) وهي الأخطر.
- **التعارض**: الأنماط مرتَّبة من الأكثر تحديداً؛ عند تداخل المواضع يفوز الأكثر تحديداً
  (رابط الدعوة قبل الرابط العام، ورقم واتساب كهاتف لا كرابط).
- **الحجب**: أرقام الهواتف تُعرض `771••••67`، الأسماء `@a•••••••v`، البريد `i••o@domain`،
  وروابط الدعوة/المسارات `https://t.me/•••`. الصيغة تُحسب مرة عند التخزين، فلا تُعرض القيمة الخام افتراضياً.

## 5) الترتيب داخل خط المعالجة

```
التقاط الهوية → فحص المحتوى/الحدود → الفلترة → حفظ المحتوى المطابق + المطابقات (matched)
             → الاستخراج + فئات التواصل + review_state (processed | failed)
```

- الاستخراج في معاملة مستقلة بعد تثبيت المحتوى؛ فشله ⇒ `failed` بلا رفع خطأ ولا إيقاف لنقطة الاستئناف (Q4).
- `TG_EXTRACTION_ENABLED=false` ⇒ يبقى المحتوى والمطابقات محفوظين وتتوقف الحالة عند `matched`.

## 7) حدود معلنة

1. الاستخراج **قائم على القرائن** فقط: رسالة بلا قرينة صريحة لا تُنتج حقولاً حتى لو كانت مفهومة للبشر.
   هذا خيار مقصود (منع الاختراع) ويحتاج توسيع قاموس القرائن بالتجربة.
2. **لا استخراج من الوسائط** (D06: لا تنزيل ولا تحليل) — لا OCR ولا صور.
3. القيم النصية قد تحمل كلمات إضافية بعد القيمة (`مبرمج بخبرة سنتين` للمسمى الوظيفي)؛ الاختصار إلى
   «أدق قيمة» مؤجَّل للخطوة السادسة حيث تُعرض الحقول داخل القالب.
4. `field_key` مجموعة ثابتة اليوم؛ القوالب المخصّصة في الخطوة السادسة ستضيف مفاتيح عبر ترحيل صريح.
5. لا واجهة لعرض نتائج الاستخراج بعد — تُعرض العدّادات فقط، وعرض الحقول/التواصل المحجوب يأتي مع
   معاينة القالب (الخطوة السادسة) لتجنّب أي كشف مبكر للمحتوى (D07/O03).
6. لم يُدَّعَ أي اختبار حيّ: كل الاختبارات على بوابة محاكاة وقاعدة PostgreSQL مدمجة.
