# المرحلة الرابعة — لوحة التحكم والتكامل النهائي والتجهيز للإطلاق

> **حالة الوثيقة:** تصوّر تقني وتصميمي **للمراجعة والاعتماد فقط**. لا كود، ولا ترحيلات، ولا تغيير في المخطط ضمن هذه الوثيقة.
> **المرجع الملزم:** `uploads/main.md` — §12 (لوحة المستخدم)، §13 (لوحة المدير)، §14 (البيانات والاحتفاظ)،
> §16 (الأمان والموثوقية)، §17 (حالات الرسائل)، §18 (دورة العمل)، §19 (النطاق)، §20 (معايير القبول)، §21 (ملاحظات ملزمة).
> **القيود القائمة الموروثة:** لا استيراد تاريخ، لا تحليل وسائط، لا ذكاء اصطناعي مدفوع، لا اقتطاع صامت، التواصل محجوب دائماً (O03)،
> حالة النشر مفصولة عن حالة المعالجة (§17)، والنشر لا يتجاوز القرارات المعتمدة D01–D12 / O01–O10.

## 1. الملخص التنفيذي

المرحلة الثالثة أغلقت **العمود الفقري**: التقاط ← معالجة ← فلترة ← استخراج ← تصنيف ← قالب ← توجيه ← تسليم ← إرسال موثوق.
لكن الواجهة الحالية لا تعرض هذا كله: صفحة `DashboardPage` ما زالت مكاناً مؤقتاً، ولوحة المدير تعرض ٦ عدّادات فقط،
ولا توجد صفحة للسجلات والأخطاء، ولا مركز إشعارات، ولا واجهة لإدارة الاحتفاظ والحذف، ولا مقاييس تشغيلية للعامل والطابور.

المرحلة الرابعة تُغلق هذه الفراغات عبر **ثلاث طبقات** لا تخلط بينها:

| الطبقة | المسؤولية | لا تفعل |
|---|---|---|
| **طبقة القراءة** (Read Model) | تجميع أرقام جاهزة للعرض بتكلفة منخفضة: عدّادات، صحة، مؤشرات أداء | لا تكتب في مسار الرسائل |
| **طبقة التشغيل** (Ops) | النبض، المقاييس، الأخطاء الموحّدة، التنبيهات، مهام الاحتفاظ | لا تعرض محتوى رسائل |
| **طبقة التجربة** (UX) | الصفحات، الحالات الفارغة، الأخطاء، التصميم الموحّد RTL | لا تكرّر منطقاً موجوداً في الخدمات |

| §16 أمان/عزل | ✅ منفّذ | CSRF، جلسات، تشفير، عزل مالك، تدقيق | مراجعة نهائية + قائمة تحقق إنتاجية |
| §20 معايير القبول (25) | 🟡 جزئي | 1–16 منفّذة/مختبَرة، 17–19 (تعديل/حذف الرسائل، متابعة كل العمليات) جزئية، 20 (لوحة المدير) ناقصة، 25 (التوثيق) جزئي | إغلاق 17–20 و25 داخل هذه المرحلة أو توثيق استثنائها بموافقتك |

> ⚠️ **بند يحتاج حسمك مبكراً:** §20/17 و§20/18 (معالجة تعديلات/حذف الرسائل) هما البند الثاني الذي أجّلناه سابقاً (Q5‑مرحلة2 + Q11: فحص `editMessageText` يدوي فقط). المرحلة الرابعة لا تفتحهما تلقائياً — انظر Q24 في §11.

## 3. المعمارية المقترحة للمرحلة الرابعة

### 3.1 مبادئ حاكمة (امتداد لما اعتُمد)

1. **لا قراءة محتوى في مسار العرض الجماعي**: كل استعلامات اللوحة تعدّ ولا تقرأ نصوصاً (امتداد D07).
2. **الأرقام من المصدر لا من ذاكرة العملية**: أي عدّاد معروض يأتي من قاعدة البيانات أو من قياس مسجَّل، لا من متغير في الذاكرة.
3. **لا منطق مكرّر**: كل صفحة تستهلك خدمة قائمة (نتائج، نشر، تيليجرام)؛ لا استعلام SQL جديد في الويب.
4. **حالة واحدة معروضة**: لكل رسالة خط زمني واحد يدمج `state` و`publish_state` و`deliveries.status` بلغة واحدة.
5. **كل عملية مدمّرة**: تأكيد صريح + تدقيق + تقرير أثر (كم صفاً حُذف).

### 3.2 وحدات جديدة (تسمية مقترحة داخل `apps/api/src/modules`)

| الوحدة | المسؤولية | تعتمد على |
|---|---|---|
| `dashboard` | قراءة تجميعية لمالك واحد: عدّادات، آخر العمليات، صحة الالتقاط والنشر | استعلامات قراءة فقط + cache قصير |
| `ops` | نبض العامل، المقاييس، فحص الجهوزية، تنفيذ مهام الاحتفاظ | `deliveryStore`, `processing`, `ingest`, `pool` |
| `logs` | سجل أخطاء موحّد (`error_events`) + واجهة قراءة | كل الخدمات تكتب فيه عبر دالة واحدة |
| `notifications` | مركز إشعارات داخلي (فوق `notification_outbox` القائم) | `ops` + الأحداث |
| `admin` (توسعة) | مقاييس النظام، إيقاف مستخدم/حساب، مراقبة الاتصالات | `dashboard`/`ops` + `users` |

### 3.3 نمط القراءة (Read Model)

```
طلب صفحة → GET /api/v1/dashboard/summary
        → DashboardService.summary(userId)
        → استعلام واحد متعدد الـ CTE (عدّادات فقط) + فهارس مخصّصة
        → cache في الذاكرة 10–15 ثانية لكل مستخدم (يُبطَل عند أي كتابة لنفس المستخدم)
```

- لا جداول لقطات في الإصدار الأول (Q16). إن تجاوز زمن الاستجابة الهدف لاحقاً ⇒ مادة عرضية (materialized view) لكل مستخدم.
- كل استعلام يحمل `user_id` في مفتاح الفهرسة الأولى.

### 3.4 خريطة الوحدات القائمة ↔ ما تعرضه اللوحة

| بيانات اللوحة | مصدرها الحالي (موجود) | ملاحظة |
|---|---|---|
| حالة حساب تيليجرام | `telegram_accounts` + `manager` (ذاكرة) | تحتاج لقطة دورية لحالة الاتصال لتعرض بعد إعادة التشغيل |
| المصادر النشطة | `telegram_sources` | عدّ بسيط |
| الفلاتر | `rule_sets` (نوع filter) | عدّ بسيط |
| القوالب | `templates` | عدّ بسيط |
| الوجهات | `destinations` | عدّ + نشط |
| رسائل مطابقة | `message_identity`/`message_matches` | عدّ بمدى زمني |
| منشورة/فاشلة | `deliveries.status` | عدّ + تفصيل آخر 24 ساعة |
| آخر العمليات | `audit_events` | يحتاج قراءة مقنَّعة (بلا محتوى) |

## 6. نموذج البيانات المقترح (ترحيلات 0018+)

> لا يُنفَّذ شيء من هذا قبل اعتماد القرارات في §11.

| الترحيل | المحتوى | لماذا |
|---|---|---|
| `0018_error_events.sql` | `error_events(id, user_id?, scope, kind, code, detail?, occurred_at, correlation_id?)` + فهارس (user, occurred_at) و(scope, kind) + سياسة احتفاظ 30 يوماً. **لا محتوى رسائل ولا نص استثناء خام.** | أساس §12.8 و§13 (Q19) |

| `0020_retention_policies.sql` | `user_settings.publish_retention_days` (موجود: `delivery_retention_days`)، `identity_retention_days` على مستوى المستخدم/النظام + جدول `retention_runs(id, policy, deleted, started_at, finished_at, error_code)` | تتبّع التنظيف وإثباته (Q23) |
| `0021_notifications.sql` | `user_notifications(id, user_id, kind, severity, title, body?, entity_type?, entity_id?, created_at, read_at)` | مركز الإشعارات (Q25) |
| `0022_read_indexes.sql` | فهارس العدّادات: `deliveries(user_id, status, created_at)`, `message_identity(user_id, publish_state, state)`, `audit_events(actor_user_id, created_at desc)` … | تحقيق أهداف الأداء (Q30) |

## 7. المراقبة والتشغيل (Ops)

### 7.1 ما يُقاس (كل مقياس له مصدر محدد)

| المقياس | المصدر | الغرض |
|---|---|---|
| `db_up`, `db_latency_ms` | `checkDatabase()` | جهوزية |
| `worker_last_seen_seconds` | `worker_heartbeats` | كشف توقف العامل |
| `queue_pending_parts`, `queue_oldest_age_seconds` | `delivery_parts` | تراكم الطابور |
| `deliveries_{published,failed,uncertain}_24h` | `deliveries` | صحة النشر |
| `ingest_last_message_at` | `message_identity` | توقف الالتقاط |
| `telegram_accounts_{connected,error}` | `telegram_accounts` + حالة المدير | صحة الحسابات |
| `publish_attempts_{retryable,permanent,uncertain}_1h` | `delivery_attempts` | جودة الاتصال بتيليجرام |
| `api_5xx_1h`, `api_p95_ms` | وسيط قياس في التطبيق (بلا محتوى) | أداء الواجهة |

### 7.2 العتبات المقترحة للتنبيه (Q26)

- العامل لم يُشاهد > 120 ثانية **و** توجد أجزاء معلّقة ⇒ تنبيه «العامل متوقف».
- أقدم جزء معلّق > 15 دقيقة ⇒ تنبيه «تأخر نشر».
- `uncertain` ≥ 1 خلال ساعة ⇒ تنبيه «نتيجة مجهولة تحتاج دليلاً».
- حساب تيليجرام `error` أو غير متصل > 5 دقائق ⇒ تنبيه.
- `api_5xx_1h ≥ 5` أو `p95 > 1000ms` ⇒ تنبيه أداء.
- إخفاق أي مهمة احتفاظ مرتين متتاليتين ⇒ تنبيه.

### 7.3 الصحة والجهوزية

- `/healthz`: 200 دائماً إن كانت العملية حيّة (تُستخدم من systemd/nginx).
- `/readyz`: 200 فقط إذا نجح فحص DB؛ وتُرفق ملخص `{db, worker, queue}` بلا تفاصيل داخلية.
- العامل يبدأ ذاتياً عند الإقلاع مع سجل صريح `worker_started` / `worker_not_started(reason)` (موجود جزئياً).

## 8. الاحتفاظ والحذف (§14)

| السياسة | النطاق | الافتراضي | من ينفّذ |
|---|---|---|---|
| احتفاظ المحتوى | نصوص الرسائل + الاستخراج + التصنيف + المطابقات | 48 ساعة (قابل للتعديل 1–2160) | مهمة قائمة (`purgeExpired`) |
| احتفاظ هوية الرسائل | كشف التكرار | حسب `TG_INGEST_IDENTITY_RETENTION_DAYS` | مهمة قائمة |
| احتفاظ سجلات النشر | `deliveries` + أجزاؤها + محاولاتها + أدلتها | 90 يوماً (`delivery_retention_days`) | **جديدة (Q13 مكتملة)** |
| احتفاظ سجلات الأخطاء | `error_events` | 30 يوماً | جديدة |
| احتفاظ التدقيق | `audit_events` | 180 يوماً (سياسة نظام) | جديدة |

**قواعد ملزمة عند الحذف:** لا يُحذف ما يخص **إعدادات** المستخدم أو جلساته أو حساباته بسبب تنظيف تشغيلي؛
كل حذف يستخدم معاملة واحدة + تقرير أثر + حدث تدقيق؛ والحذف اليدوي يتطلب كتابة عبارة تأكيد.

## 9. التجهيز للإطلاق (Production Readiness)

| البند | المطلوب | الحالة |
|---|---|---|
| الأسرار | كل المفاتيح في `env` فقط، ولا شيء في Git (`TG_SESSION_ENC_KEY`, `TG_BOT_ENC_KEY` + نسخ سابقة للتدوير) | ✅ |
| متغيرات البيئة | توثيق كامل لكل متغير + قيم افتراضية آمنة + فشل صريح عند نقص حرج | 🟡 يحتاج تدقيق نهائي |
| الترحيلات | «إلى الأمام فقط» + بصمة + فحص قبل الإقلاع | ✅ |
| النسخ الاحتياطي | `pg_dump` دوري + إجراء استعادة موثّق + اختبار استعادة فعلي (Q28) | ❌ |
| التشفير في النقل | TLS عبر nginx (أو ما يعادله) + HSTS + كوكيز `Secure` | ❌ (تطويري) |
| التشغيل | systemd unit + إعادة تشغيل تلقائي + `SIGTERM` لطيف (موجود) + حدود ذاكرة | 🟡 |
| السجلات | pino منظّم + `request_id` + دوران ملفات + بلا محتوى/أسرار | 🟡 |
| الحدود | rate limit لكل مسار حسّاس + حدود الموارد (نتائج/تسليمات/وجهات) | 🟡 |
| الأداء | أهداف: p95 للـ API < 300ms، لوحة < 500ms، دورة عامل ≤ 3s | ❌ (يُقاس في P4‑د) |
| التوثيق | `README` + `LOCAL-SETUP` + دليل تشغيل (Runbook) + دليل صيانة | 🟡 |
| الاختبارات | بوابة كاملة + **اختبار رحلة كاملة** (تسجيل ← ربط ← مصدر ← فلتر ← قالب ← نشر ← ظهور الأرقام في اللوحة) | 🟡 (الرحلة غير موجودة) |

## 11. القرارات المطلوبة قبل كتابة أي كود (Q16–Q31)

> صيغة كل قرار: السؤال · الخيارات · **توصيتي** · أثر رفض التوصية. الموافقة الجماعية ممكنة («أوافق على الكل») أو تعديل فردي.

### المجموعة أ — القراءة والعرض

**Q16 — نمط قراءة اللوحة؟**
(أ) استعلامات تجميعية حيّة + cache 10–15 ثانية + فهارس مخصّصة · (ب) مادة عرضية (materialized view) تُحدَّث كل N دقيقة · (ج) جدول عدّادات يُحدَّث بالكتابة.
**توصيتي: (أ)** — أبسط وأصدق («الأرقام من المصدر»)، ويُنقل إلى (ب) فقط إن تجاوز p95 الهدف. رفضها ⇒ تعقيد إضافي بلا داعٍ الآن.

**Q17 — نقاط الصحة والمقاييس وتعرّضها؟**
(أ) `/healthz` + `/readyz` عامّتان مختصرتان + `/admin/metrics` للمدير فقط · (ب) إضافة صيغة Prometheus عامة محمية برمز · (ج) الاقتصار على `/api/v1/health` الحالي.
**توصيتي: (أ)** — يخدم systemd/nginx والمدير بلا كشف تفاصيل. رفضها ⇒ إما لا مراقبة آلية (ج) أو حاجة لوكيل مراقبة (ب).

**Q18 — رقابة العامل: نبض أم لا؟**
(أ) جدول `worker_heartbeats` + عرض في `/admin/system` + تنبيه عند التوقف · (ب) الاعتماد على السجلات فقط · (ج) نقل العامل إلى عملية مستقلة الآن.
**توصيتي: (أ)** — إثبات حياة بعد إعادة التشغيل بلا تعقيد نشر. (ج) تُؤجَّل حتى يثبت الحمل حاجتها.

### المجموعة ب — السجلات والإشعارات

**Q19 — سجل أخطاء موحّد (`error_events`)?**
(أ) نعم، 30 يوماً، بلا نصوص رسائل ولا استثناءات خام · (ب) الاستنتاج من `last_error_code` + السجلات النصية فقط · (ج) نعم مع احتفاظ أطول (180 يوماً).
**توصيتي: (أ)** — §12.8/§13 يحتاجان مصدراً موحّداً قابلاً للتصفية، وبلا محتوى.

**Q25 — الإشعارات: قناة أم مركز داخلي؟**
(أ) مركز إشعارات داخلي فقط في v1 (بريد لاحقاً عبر `notification_outbox` القائم) · (ب) بريد فوري الآن (يحتاج مزوّد SMTP وأسراراً جديدة) · (ج) لا إشعارات (عرض فقط).
**توصيتي: (أ)** — لا إضافة اعتماد خارجي قبل الإطلاق؛ التصميم يبقي الباب مفتوحاً.

**Q26 — عتبات التنبيه؟** القيم في §7.2 (عامل 120 ثانية، تأخر نشر 15 دقيقة، `uncertain` ≥ 1/ساعة، انقطاع حساب 5 دقائق، 5xx ≥ 5/ساعة).
**توصيتي: اعتمادها كبداية قابلة للتعديل من `/admin/settings`** — بلا قيم ثابتة في الكود.

### المجموعة ج — التدمير والاحتفاظ

**Q20 — دلالات «إعادة النشر» (§12.7)?**
(أ) مسموحة فقط لتسليم `failed`/`cancelled`/`blocked`؛ إعادة تخطيط بخطة جديدة، احترام سياسة الطول والحجب، حد 3 مرات، تدقيق — و**ممنوعة تماماً على `uncertain`** (تحتاج دليلاً) · (ب) مسموحة لكل الحالات عدا `published` · (ج) غير مطلوبة في v1.
**توصيتي: (أ)** — تحفظ معنى O04 ومنع النشر المزدوج.

**Q21 — الحذف اليدوي للبيانات؟**
(أ) «حذف بياناتي التشغيلية الآن»: محتوى + استخراج + تصنيف + مطابقات + تسليمات + أجزاؤها + محاولاتها + أدلتها — **ولا يمسّ** الإعدادات/الجلسات/الحسابات/التدقيق · (ب) الحذف الكلي فقط عبر حذف الحساب · (ج) لا حذف يدوي.
**توصيتي: (أ)** مع تأكيد بعبارة + تقرير أثر + تدقيق؛ والمدير يستطيع تنفيذها لمستخدم بسبب إلزامي.

**Q22 — حذف الحساب؟**
(أ) حذف فوري نهائي: إبطال كل الجلسات + مسح أسرار تيليجرام والبوت + مسح البيانات + إبقاء سجل تدقيق بلا PII · (ب) soft-delete مع فترة سماح 7 أيام · (ج) تعطيل فقط.
**توصيتي: (أ)** — أبسط وأوضح التزاماً بـ§14، و«التعطيل» (ج) يبقى متاحاً للمدير كإجراء منفصل.

**Q23 — من ينفّذ مهام الاحتفاظ؟**
(أ) مشغّل دوري واحد داخل العملية (`ops.scheduler`) يضم كل السياسات مع `retention_runs` ومقاييس · (ب) مهام متفرقة كما اليوم · (ج) cron خارجي.
**توصيتي: (أ)** — مكان واحد للمراقبة والاختبار؛ (ج) لاحقاً عند تعدّد النسخ.

### المجموعة د — الأمان والنطاق

**Q24 — هل يُفتح للمدير أي وصول لمحتوى المستخدمين (D07/O07)?**
(أ) **لا** في v1: لوحة المدير تشغيلية فقط · (ب) وصول مؤقت مبرَّر بتدقيق · (ج) وصول دائم.
**توصيتي: (أ)** — يحفظ العزل، ويُغلق معيار §20/17–18 بالتوثيق لا بالكشف.

**Q27 — نموذج التشغيل الإنتاجي؟**
(أ) عملية Node واحدة تحت systemd + nginx لـTLS · (ب) PM2/حاويات · (ج) منصة سحابية مُدارة.
**توصيتي: (أ)** — يطابق «الاستضافة محلية أو سحابية» (§15) بلا اعتماد إضافي.

**Q28 — النسخ الاحتياطي والاستعادة والمفاتيح؟**
(أ) `pg_dump` يومي + احتفاظ 14 نسخة + Runbook استعادة مُختبَر + تدوير مفاتيح سنوي (النسخة السابقة مدعومة) · (ب) لاحقاً بعد الإطلاق · (ج) بدون نسخ.
**توصيتي: (أ)** — الشرط 25 من §20 يذكر الصيانة صراحةً.

**Q29 — تتبّع موزّع (OpenTelemetry) في v1?**
(أ) لا: pino منظّم + `request_id` + `correlation_id` لمسار الرسالة · (ب) نعم الآن · (ج) لاحقاً.
**توصيتي: (أ)** — كفاية تشخيصية بلا اعتماد تشغيلي جديد.

**Q30 — الترقيم والأداء؟**
(أ) ترقيم مؤشر (cursor) لكل القوائم + فهارس §6 + أهداف §9 · (ب) `limit/offset` الحالي · (ج) بلا حد.
**توصيتي: (أ)** — `offset` ينهار مع حجم السجلات، و«بلا حد» غير آمن.

**Q31 — بوابة القبول النهائية؟**
(أ) اختبار «رحلة كاملة» إلزامي في البوابة (تسجيل ← ربط ← مصدر ← فلتر ← قالب ← مسار ← إرسال مزيّف ← ظهور الأرقام في اللوحة) بأسماء مزيّفة · (ب) اختبارات وحدات فقط · (ج) فحص يدوي.
**توصيتي: (أ)** — هو الترجمة العملية لمعايير §20 ويحمي من انحدار التكامل.

## 12. المخاطر والحدود المعلنة (بلا تجميل)

1. **حالة اتصال تيليجرام تعيش في الذاكرة** (`manager`)؛ بعد إعادة التشغيل تُستعاد بحدود (D03) لكن اللوحة تحتاج لقطة مسجَّلة لتُظهر «آخر حالة معروفة + وقتها» بدل ادّعاء «متصل». (يدخل في P4‑ب.)
2. **لا استيراد تاريخ ولا استعادة رسائل الفجوة** — ستُكتب هذه الحدود نصاً في صفحة الحسابات (§11).
3. **حدود معدّل تيليجرام** لا تُلغى بالواجهة؛ أي «إعادة نشر» أو «تسريع» يبقى خاضعاً لـ1.2 ثانية/محادثة و429.
4. **العامل داخل العملية**: توقّف العملية = توقّف الإرسال (يُكشف بالنبض والتنبيه، لا يُعالَج بنسخة ثانية الآن).
5. **لا تعرّض لأي محتوى في لوحة المدير** يعني أن تشخيص «لماذا فشل نشر رسالة معيّنة» يتطلب من المستخدم فتح تفصيل تسليمه — وهو مسار مقصود (D07).
6. **الأداء غير مُقاس بعد** على بيانات حقيقية؛ أهداف §9 تفتراضية تُعتمد أو تُعدَّل.

## 13. ما لا تدخله المرحلة الرابعة (صراحةً)

- تعديل/حذف الرسائل المنشورة، وفحص `editMessageText` التلقائي (Q5‑مرحلة2 + Q11 يبقيان مؤجّلين).
- تحليل الوسائط، استيراد التاريخ، ذكاء اصطناعي مدفوع، اشتراكات/مدفوعات، تطبيق هاتف.
- عمليات عامل متعددة أو توزيع أفقي (يُنقل إليها فقط عند الحاجة المثبتة).
- إشعارات بريدية فعلية ما لم يُعتمد خيار (ب) في Q25.
