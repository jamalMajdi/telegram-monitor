# التجهيز للإنتاج — مراجعة الأمان والحدود وأهداف الأداء (P4‑ز)

> **الغرض:** ما يحتاج مدير النظام معرفته **قبل** رفع النظام: ما هو محمي فعلاً، ما هو محدود بالتصميم،
> وما هي الأرقام التي يمكن الاعتماد عليها. كل ما هنا مُتحقَّق من الكود والاختبارات والقياس، لا تقديرات تسويقية.
> المرافق: `docs/runbook.md` (خطوات التشغيل)، `docs/decisions-traceability.md` (تتبّع كل قرار).

---

## 1) نموذج التهديد في سطر

النظام يعالج **بيانات حساسة بطبيعتها**: نصوص رسائل تيليجرام، وأرقام تواصل، ورموز بوتات، وجلسات MTProto.
لذلك المبدأ الحاكم: **لا يُخرَج المحتوى من مكانه الأصلي إلا بالحد الأدنى**، ولا يُخزَّن سرّ بلا تشفير،
ولا يُسجَّل شيء يمكن أن يُعرف به صاحب الرسالة.

| الأصل | أين يعيش | الحماية |
| --- | --- | --- |
| نصوص الرسائل | `message_content` فقط، وتموت بالاحتفاظ | عزل `user_id`، تقنين في العرض، لا سجلات |
| أرقام التواصل | لا تُخزَّن خاماً في أي استجابة | تُقنَّع قبل العرض؛ لا وجود لها في السجلات/التدقيق/المنشور |
| رموز البوتات | مشفّرة AES‑256‑GCM (`TG_BOT_ENC_KEY`) | لا تُعاد أبداً في أي استجابة أو سجل |
| جلسات MTProto | مشفّرة AES‑256‑GCM (`TG_SESSION_ENC_KEY`) | مفتاح مستقل، تدوير بسلف (`*_PREVIOUS`) |
| كلمات مرور المستخدمين | scrypt مع ملح لكل صف | لا تُسجَّل ولا تُعاد |
| كوكي الجلسة | HttpOnly + SameSite + Secure في الإنتاج | إبطال فوري عند الحذف/التعطيل |

| # | الملاحظة | الأثر | التخفيف |
| --- | --- | --- | --- |

## 3) أهداف الأداء وحدود النظام

### 3.1 قياسات حقيقية (P4‑ز، 50,000 رسالة، PostgreSQL 17، جهاز تطوير)

| العملية | الزمن | ملاحظة |
| --- | --- | --- |
| صفحة النتائج الأولى (25 صفاً) | **8 ms** (بارد) / 3 ms (دافئ) | مع فلترة المستخدم |
| الصفحة 20 (500 صف عمقاً) | **2.0 ms** | — |
| الصفحة 100 (2,500 عمقاً) | **2.0 ms** | — |
| الصفحة 200 (5,000 عمقاً) | **1.9 ms** | **ثابت**: المؤشِّر لا يتباطأ مع العمق |
| نفس العمق بالطريقة القديمة (`offset`) | **30 ms** | 15× أبطأ وينمو خطياً ⇒ سبب اعتماد المؤشِّر (Q30) |
| الخط الزمني لرسالة واحدة | **10 ms** | 8 جداول مُدمجة للقراءة |
| عدّادات لوحة المستخدم | **5.5 ms** | تُخزَّن 15 ثانية في الذاكرة |
| اختبار فلتر (في الذاكرة) | < 5 ms | بلا قاعدة بيانات أصلاً |

> منهجية: `EXPLAIN` + قياس زمن الاستدعاء عبر المستودع الحقيقي على قاعدة مُبذورة بـ`generate_series`.
> الأرقام على جهاز التطوير؛ على خادم الإنتاج توقّع أبطأ بنسبة معقولة بحسب القرص والذاكرة.

### 3.2 حدود مضمّنة في التصميم (يعرفها المدير قبل الرفع)

| الحد | القيمة | المصدر |
| --- | --- | --- |
| التزامن في الإرسال | **≤ 3** أجزاء متزامنة | §10.6 |
| الفاصل بين رسالتين لنفس المحادثة | **1.2 ثانية** | §10.5 |
| حدّ طول المنشور | 4096 حرفاً **بعد** معالجة الكيانات | §10.3 |
| مصادر لكل حساب تيليجرام | 25 | `TG_MAX_SOURCES_PER_ACCOUNT` |
| وجهات نشر لكل مستخدم | 20 | `TG_MAX_DESTINATIONS_PER_USER` |
| مسارات نشر لكل مستخدم | 50 | `TG_MAX_ROUTES_PER_USER` |
| إعادة نشر لكل تسليم | **3** (وفي المخطط قيد يرفض 4) | Q20 |
| حجم جسم الطلب | 64KB (تطبيق) / 256KB (nginx) | `express.json`, nginx |
| صفحة قوائم | ≤ 100 عنصر | Q30 |
| تجمّع اتصالات القاعدة | 10 | `DB_POOL_MAX` |
| دورة عامل النشر | 3 ثوانٍ | `TG_PUBLISH_WORKER_INTERVAL_MS` |
| استحواذ الجزء (lease) | 90 ثانية | `TG_PUBLISH_LEASE_SECONDS` |
| عتبة «العامل متوقف» | 120 ثانية | `TG_OPS_WORKER_STALE_SECONDS` |
| احتفاظ المحتوى الافتراضي | 24 ساعة (قابل للضبط لكل مستخدم) | `user_settings` |
| احتفاظ الهويات | 30 يوماً | `TG_INGEST_IDENTITY_RETENTION_DAYS` |
| احتفاظ سجل الأخطاء | 30 يوماً | `system.error_events_retention_days` |
| احتفاظ التدقيق | 180 يوماً | `system.audit_retention_days` |
| احتفاظ التسليمات | 90 يوماً (لكل مستخدم) | `user_settings.delivery_retention_days` |
| نسخ احتياطي | 14 نسخة يومية | `BACKUP_KEEP` |

### 3.3 سعة تقديرية (V1)

- **الالتقاط**: محدود بمعدل رسائل المصادر ومكتبة MTProto، لا بالنظام.
- **الإرسال**: القيد الحقيقي هو الفاصل 1.2 ثانية لكل محادثة ⇒ ~50 رسالة/دقيقة لكل وجهة كحد أقصى نظري،
  مع تزامن ≤3 يوزّع الحمل بين الوجهات.
- **التخزين**: كل رسالة مطابقة ≈ 2–6 KB (نص + استخراج + مطابقات) قبل الاحتفاظ؛ 50 ألف رسالة/شهر
  ≈ 150–300 MB مع احتفاظ 24 ساعة ونسخ احتياطية يومية.
- **القراءة**: القوائم ثابتة الزمن مهما كبر الأرشيف بفضل المؤشِّرات (3.1). اللوحة تعتمد `count(*)` مُفهرسة؛
  عند ملايين الصفوف يُنقل إلى لقطات مجدولة (خارج V1، موثَّق).

## 4) قائمة تحقّق ما قبل الرفع (Sign‑off)

**البنية**
- [ ] خادم محدَّث، جدار حماية يفتح 80/443 فقط، `ss` لا يُظهر 4000/5432 على `0.0.0.0`
- [ ] PostgreSQL 16+، دور مخصّص (لا superuser)، `pg_hba` بـ`scram-sha-256`
- [ ] `npm run build` ينتج `apps/api/dist` **مع** `dist/db/migrations` (25 ملفاً) و`apps/web/dist`

**البيئة**
- [ ] `/etc/tg-monitor/api.env` بصلاحية `640 root:tgmon` ومكتمل حسب §5 في runbook
- [ ] المفتاحان (**مختلفان**) مولَّدان و`*_PREVIOUS` فارغ في أول إطلاق
- [ ] `APP_ORIGIN` و`COOKIE_SECURE=true` و`NODE_ENV=production` و`DEV_EXPOSE_RESET_TOKEN=false`

**الخدمة**
- [ ] `tg-migrate` نجح (25 ترحيلاً، 0 متجاوزة)
- [ ] `tg-api` نشطة: `systemctl status tg-api` = active (running)
- [ ] `/healthz` و`/readyz` = 200، و`publishWorker.state = ok` (أو `missing` قبل أول دورة — يزول بعد 3 ثوانٍ)
- [ ] `healthcheck.sh` يعيد 0
- [ ] `systemd-analyze verify` نظيف على الوحدات الأربع

**الأمان**
- [ ] HTTPS يعمل، إعادة توجيه 80→443، `curl -I` يُظهر HSTS وCSP
- [ ] محاولة دخول خاطئة متكررة تُقفل الحساب مؤقتاً
- [ ] تسجيل مستخدم ثانٍ: لا يرى نتائج الأول (فحص يدوي سريع)
- [ ] `journalctl -u tg-api` بلا أي نص رسالة أو رقم تواصل أو رمز

**النسخ والاستعادة**
- [ ] `systemctl start tg-backup` أنتج ملفاً + بصمة، و`restore.sh --verify` نجح
- [ ] تمرين استعادة إلى `tg_restore_drill` نجح والأعداد متطابقة، ثم حُذفت القاعدة
- [ ] النسخ تُنسخ خارج الخادم (rsync/rclone) ومُجرَّبة

**التشغيل**
- [ ] أول مدير أُنشئ و`BOOTSTRAP_ADMIN_EMAIL` أُفرغ
- [ ] حساب تيليجرام واحد مربوط، مصدر واحد، فلتر واحد، بوت نشر، وجهة، ومسار فعّال
- [ ] رسالة تجريبية وصلت الوجهة، وظهرت في النتائج وفي الخط الزمني، وارتفعت أرقام اللوحة
- [ ] مركز التنبيهات يعرض الحالات المتوقعة، والاعتراف يعمل
- [ ] `tg-backup.timer` نشط، وسياسة الاحتفاظ مضبوطة

## 5) ما لا يفعله هذا النظام (حدود صريحة)

- **لا تعديل ولا حذف للرسائل المنشورة** (§20/17–18) — خارج V1 بقرار صريح.
- **لا إعادة إرسال تلقائية** لنتيجة مجهولة (O04) — الدليل البشري شرط.
- **لا وصول مدير لمحتوى المستخدم** (Q24) — المقاييس أعداد فقط.
- **لا قنوات إشعار خارجية** (بريد/تيليجرام) — مركز تنبيهات داخلي.
- **لا تعدد عُقد/HA** — عملية واحدة + PostgreSQL واحد؛ التوسع الأفقي يحتاج مراجعة القفل والـleases.
- **لا WebSocket** — تحديث الشارة كل 60 ثانية.
- **لا تكامل مع مزوّد بريد** — استعادة كلمة المرور يديرها المدير.
