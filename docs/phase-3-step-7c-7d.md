# المرحلة الثالثة — الدفعتان 7‑ج و7‑د: التنسيق والتقسيم، عامل الإرسال، والمراجعة

> **النطاق:** مكتمل حسب التصميم المعتمد (`docs/phase-3-design.md`) وشروط المستخدم الصريحة للدفعتين.
> **لم يُرسل أي منشور حقيقي إلى تيليجرام:** لا يوجد بوت حقيقي مربوط، وكل اختبارات الإرسال عبر عميل Bot API مزيّف.
> **الالتزامات الأربعة الحرفية:** قياس الطول بعد تحليل الكيانات · حجب مزدوج وأي فشل ⇒ رفض آمن ·
> حفظ المحاولة قبل طلب HTTP · النتيجة المجهولة لا تُعاد تلقائياً وتحتاج دليلاً بشرياً · اللُقى تمنع الإرسال المتزامن.

## 1) ما نُفِّذ

### 7‑ج — التنسيق والحجب والتقسيم

| البند | التنفيذ | المرجع |
|---|---|---|
| قياس الطول بعد تحليل الكيانات | `htmlVisibleText` يفكّ الكيانات ثم `Array.from` للعد بوحدات Unicode | `publisher.ts` |
| الترميز الآمن | `escapeHtml` لكل قيمة قبل البناء؛ لا HTML من المصدر | `publisher.ts` |
| الإخفاء النهائي (O03) | `enforceMasking` يعيد كشف أصناف التواصل على النص المبني ويعيد حجبها ويقلب المدى | `publisher.ts` + `contactDetector` |
| فشل الحجب ⇒ رفض | `planPost` يعيد `masking_failed` ويُغلق التسليم `blocked` بلا أجزاء | `planPost`, `DeliveryPlanner` |
| التقسيم (Q5) | جملة ← مسافة ← قطع حتمي، بلا كسر زوج بديل، وبلا اقتطاع صامت | `splitValue`, `planPost` |
| سياسة «رفض» | نص يتجاوز الحد أو `maxParts` ⇒ `too_long` وإغلاق بلا إرسال | `planPost` |
| لا ترقيم (Q6) | الأجزاء نص متصل بلا لاحقة «(1/3)» | `planPost` |
| تثبيت الخطة | `delivery_parts` بفهرس فريد ونص منسَّق وبصمة `sha256` و`char_count` بعد التحليل | `savePlan`, `0017` |
| إعادة التخطيط | ترفع `plan_version` وتستبدل الأجزاء في معاملة واحدة | `savePlan` |
| احتفاظ المحتوى | لا تخطيط بعد الانتهاء ⇒ `blocked/content_expired` وإزالة أي أجزاء سابقة | `DeliveryPlanner.plan` |
| نص بلا قالب | يُبنى من نص الرسالة نفسه (لا اختراع حقول ولا تسميات) | `assembleSource` |

**قياسات فعلية (اختبارات):** `publish-formatting.test.ts` = 15/15 · `publish-plan.test.ts` = 6/6.

### 7‑د — عامل الإرسال، المحاولات، المراجعة، والمجهول

| البند | التنفيذ | المرجع |
|---|---|---|
| المحاولة قبل HTTP | `openAttempt` يُنشئ صف `delivery_attempts(outcome='started')` **قبل** `sendMessage` ثم يُغلق بعد الاستجابة | `DeliveryWorker.sendPart` (مُختبَر باستعلام داخل طلب الإرسال) |
| اللُقية المزدوجة | استحواذ على التسليم **و** الجزء بـ`lease_owner/lease_expires_at` + `for update … skip locked` | `claimPart` |
| استعادة اللُقى المنتهية | الجزء يعود `pending` والتسليم `queued` بلا إرسال مكرر | `recoverExpiredLeases` |
| تزامن ≤3 (Q10) | `concurrency` محدود بسقف 3 داخل العملية | `DeliveryWorker` |
| فاصل المحادثة | ١.٢ ثانية لكل `chat_id` قبل كل محاولة | `ChatSpacer` |
| تصنيف الأخطاء | قابل للإعادة: **429 وحده** · نهائي: 401/403/400/`too_long`/`chat_not_found` · **مجهول: شبكة/مهلة/5xx/غير متوقع** | `classifySendFailure` |
| احترام 429 | `next_attempt_at = now + retry_after` حرفياً (والأبعد بينه وبين التباعد) | `planRetry` |
| سقف Q12 | 5 محاولات و6 ساعات من إنشاء التسليم ثم `retry_exhausted` | `planRetry` |
| O04 | المجهول ⇒ الجزء والتسليم `uncertain`، بلا جدولة إعادة، ويحتاج دليلاً بشرياً | `markPartStopped`, `delivery_evidence` |
| تسوية المجهول | `POST /publish/deliveries/:id/evidence` (`message_id` أو `manual_check`) ⇒ `published` أو `failed`، ومرة واحدة فقط | `DeliveryStore.recordEvidence` |
| الحالة النهائية | تُحسب من حالات الأجزاء لا من نيّة العامل، وتُنقل شفرة الخطأ النهائية إلى التسليم | `finalizeDelivery` |
| المراجعة البشرية | اعتماد ⇒ `queued` + `approved_version = plan_version`؛ رفض ⇒ `cancelled` بلا إرسال | `DeliveryService.review` |
| إبطال الموافقة | إعادة التخطيط تُبطل الموافقة (شرط في استعلام الاستحواذ) | `claimPart` |
| وجهة معطّلة | التسليم يُغلق `blocked/destination_inactive` بلا إرسال | `blockUnroutableDestinations` |
| فحص أخير قبل الإرسال | نص مرئي 0 أو >4096 ⇒ `length_violation` ولا إرسال | `sendPart` |
| الرمز والبوت | يُقرأ الرمز قبل المحاولة؛ فشله ⇒ `bot_unavailable` بلا استهلاك محاولة إرسال | `sendPart` |
| السجلات | لا رمز بوت ولا نص رسالة ولا قيمة تواصل خامة في `delivery_attempts` | `0017`, `redactToken` |
| الواجهة | تفصيل تسليم (أجزاء + محاولات + أدلة)، اعتماد/رفض، ونموذج دليل للمجهول | `TelegramPublishPage.tsx` |

**قياسات فعلية (اختبارات):** `publish-worker.test.ts` = 11/11 (يشمل: المحاولة قبل HTTP، منع المراجعة، الرفض، 429، 403، المجهول ثم الدليل، استنفاد المحاولات، اللُقية، الوجهة المعطّلة، فاصل المحادثة).

## 2) واجهات API المضافة

| الطريقة | المسار | الغرض |
|---|---|---|
| GET | `/api/v1/telegram/publish/deliveries/:id` | تفصيل: الأجزاء (نص محجوب)، سجل المحاولات (بلا نص)، الأدلة |
| POST | `/api/v1/telegram/publish/deliveries/:id/approve` | اعتماد بشري ⇒ `queued` (409 إن لم يكن بانتظار مراجعة، 404 إن لم يوجد) |
| POST | `/api/v1/telegram/publish/deliveries/:id/reject` | رفض ⇒ `cancelled` بلا إرسال |
| POST | `/api/v1/telegram/publish/deliveries/:id/evidence` | دليل بشري لنتيجة مجهولة (مرة واحدة، وإلا 409) |

كل المسارات محمية بالجلسة وCSRF، وتعمل داخل مساحة مالكها فقط.

## 5) ما لم يُنفَّذ (مقصود ومعلن)

1. **لا إرسال حقيقي** إلى تيليجرام: لا بوت حقيقي مربوط، وكل الإرسال في الاختبارات عبر عميل مزيّف.
2. **تنظيف دوري لسجلات النشر (Q13)** حسب `delivery_retention_days`: لم يُضف في هذه الدفعة (العمود والسياسة موجودان، والتنظيف نفسه مؤجَّل صراحةً).
3. **فحص `editMessageText`** (Q11) بقي **يدوياً صريحاً فقط**؛ لا استدعاء تلقائي في الكود، ولا واجهة له.
4. **تعديل/حذف الرسائل المنشورة** (Q5 مرحلة 2) مؤجَّل كما هو.
5. **حد 20 رسالة/دقيقة للمجموعات**: الحماية العاملة هي فاصل ١.٢ ثانية لكل محادثة + احترام 429؛ لا عدّاد نافذة دقيقة مستقل بعد.

## 6) قرارات اعتمدها المستخدم بعد التقرير الأول

| القرار | الأثر | الحالة |
|---|---|---|
| **5xx ⇒ «مجهول» لا «قابل للإعادة»** | `classifySendFailure` يردّ `server_unknown`؛ لا إعادة تلقائية، ودليل بشري مطلوب. الاختبارات: `429` وحده يختبر استنفاد السقف، وأُضيف اختبار مخصص لـ5xx | **مطبَّق ومُختبَر** (`publish-worker.test.ts` 11/11) |
| **تسلسل الأجزاء يتقدّم على السرعة** | الاستحواذ على مستوى التسليم يبقى كما هو (جزء واحد في كل مرة لكل تسليم) | **مُعتمد كما هو** |

## 7) ملاحظات تشغيلية

- **`plan_version` يبدأ من 1 بمعنى «بلا خطة»**، فالتخطيط الأول يرفعه إلى 2. موثَّق في الاختبار و`database.md`.
- **مشغّل الاختبارات** (`apps/api/scripts/run-tests.mjs`): كل ملف اختبار يقيم قاعدة PostgreSQL مضمَّنة في `/tmp`، وتشغيل 15 قاعدة معاً يتجاوز مساحة القرص المؤقتة في البيئات المحدودة فيفشل بلا علاقة بالكود. المشغّل الآن: اختبارات الوحدة بالتوازي الكامل، ثم اختبارات قاعدة البيانات بتسلسل (‎1). النتيجة: البوابة كاملة في ~80 ثانية وبلا تقلّب.
