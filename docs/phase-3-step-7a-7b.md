# المرحلة الثالثة — الدفعتان 7‑أ و7‑ب: البوت والوجهات، والتوجيه ومنع الحلقات

> **النطاق:** مكتمل حسب التصميم المعتمد في `docs/phase-3-design.md` بعد موافقة المستخدم على Q1–Q15.
> **لا إرسال فعلي إلى تيليجرام في هذه الدفعة**: لا `sendMessage`، ولا طابور إرسال، ولا محاولات، ولا أجزاء منشورة.
> ما يُنشأ هنا: بوت مشفّر ومتحقَّق، وجهات بصلاحيات مثبتة، مسارات، **حواف توجيه**، و**تسليمات مسجّلة**.

## 1) ما نُفِّذ

### 7‑أ — بوت النشر والوجهات

| البند | التنفيذ | المرجع |
|---|---|---|
| بوت واحد لكل مستخدم (Q9) | `publish_bots` بقيد `unique (user_id)`، وتحديث الرمز = upsert على الصف نفسه | `0014`, `botService.ts` |
| تشفير الرمز (Q1) | مغلّف AES‑256‑GCM نفسه المستخدم للجلسات، بمفتاح مستقل `TG_BOT_ENC_KEY` ودعم سابق للتدوير | `botCipher.ts`, `sessionCipher.sealWithKey/openWithKeys` |
| ربط الرمز بصفه (AAD) | `tg-bot:v1:<botRowId>:<keyVersion>` ⇒ نقل مغلّف إلى صف آخر يُفشل الفك (مُختبَر) | `botCipher.ts` |
| لا إظهار للرمز أبداً | لا يُعاد في أي استجابة/سجل/تدقيق؛ التنقية `[redacted]` في أخطاء Bot API | `botApiClient.redactToken`, `publishing-bots-destinations.test.ts` |
| عميل Bot API (Q2) | `fetch` + مهلة 10s + تصنيف أخطاء حتمي (`botApiClient.ts`)؛ لا رمز في أي رسالة خطأ | `bot-api-client.test.ts` |
| تحقق قبل الإضافة | `getMe` للبوت، ثم `getChat` + `getChatMember` للوجهة | `botService.connect`, `destinationService.add` |
| قواعد حق النشر | القناة: مشرف + `can_post_messages`؛ المجموعة: عضوية أو إدارة | `evaluateRights` (مُختبَرة وحدها) |
| سحب الصلاحية | `403`/`chat not found` ⇒ الوجهة `revoked` + تعطيل مساراتها وحذف حوافها | `destinationService.verify` |
| إيقاف/استئناف | `paused` / إعادة تحقق إلزامية قبل العودة إلى `active` | `pause`/`resume` |
| حذف الوجهة (Q15) | `deleted` (تعطيل) مع إبقاء السجل + تعطيل المسارات وحذف الحواف | `destinationService.remove` |
| واجهة المستخدم | صفحة «النشر إلى تيليجرام»: ربط البوت، إضافة وجهات، تحقق/إيقاف/حذف | `TelegramPublishPage.tsx` |

### 7‑ب — التوجيه، المسارات، منع الحلقات، التسليمات

| البند | التنفيذ | المرجع |
|---|---|---|
| شروط المسار (Q3) | مصادر/فلاتر/تصنيفات، الانطباق **بأيٍّ منها**؛ مسار بلا شروط يُرفض | `route_scopes`, `routeService.validateScopes` |
| القالب (O02) | قالب المسار يتقدّم على المختار في المعالجة، ويُخزَّن على التسليم | `planDeliveries`, `deliveries.template_id` |
| المراجعة (D01 + Q4) | طلب أي مسار للمراجعة يُلزم الوجهة كلها، و`needs_review` يفرضها ولو كان المسار تلقائياً | `planDeliveries` (4 اختبارات وحدة) |
| التسليم المنطقي (D05) | `unique (identity_id, destination_id)` + `on conflict do nothing` | `0016`, `routingService.routeMessage` |
| الذرّية | إنشاء التسليمات + تحديث `message_identity.publish_state` في معاملة واحدة | `routingService` |
| منع الحلقات (O05) | قفل استشاري + بناء حواف بمعرّفات فنية + `WITH RECURSIVE` لكشف الدورات، كلها في معاملة التفعيل | `routeService.applyActivation`, `publishRepository.findCyclePath` |
| تقريب محافظ | مسار بشرط غير مصدر ⇒ تُبنى حواف **كل** مصادر المستخدم (رفض أكثر لا أقل) | `applyActivation` |
| رفض محايد | `routing_cycle_detected` برسالة واحدة بلا أي تفصيل عن مسار الغير (مُختبَر عبر مستخدمين) | `loopGuard.CYCLE_REJECTION_MESSAGE` |
| إعادة الفحص عند التعديل | تعديل مسار فعّال يُعاد بناؤه وفحصه في المعاملة نفسها؛ الفشل يلغي التعديل | `routeService.update` |
| تعطيل/حذف | حذف الحواف مع كل تعطيل أو حذف (لا حواف «يتيمة») | `deactivate`/`remove` |
| الربط بخط المعالجة | التوجيه بعد التصنيف واختيار القالب؛ فشله **لا** يحوّل الرسالة إلى `failed` | `messageProcessingService` step 6 |
| واجهة المستخدم | إنشاء مسار (وجهة + شرط + قالب + سياسة)، تفعيل/تعطيل/حذف، وسجل التسليمات | `TelegramPublishPage.tsx` |

## 2) تدفق الدفعة كما نُفِّذ

```
تطابق فلتر ⇒ حفظ المحتوى ⇒ استخراج ⇒ تصنيف + قالب ⇒ [7-ب] RoutingService.routeMessage
                                                          │
        مسارات فعّالة + وجهات فعّالة، مطابقة بأي شرط ────────┤
                                                          ▼
                         خطة: تسليم واحد لكل وجهة (D05) + قرار مراجعة + قالب
                                                          │  (معاملة واحدة)
                          deliveries(awaiting_review | queued) + publish_state
```

## 3) الحالات المُنفَّذة

| الكائن | الحالات | الانتقالات المنفَّذة |
|---|---|---|
| البوت | `active` / `invalid` / `disabled` | ربط/تحقق ⇒ `active`؛ فشل `getMe` ⇒ `invalid`؛ تعطيل يدوي ⇒ `disabled` |
| الوجهة | `pending` / `active` / `paused` / `revoked` / `error` / `deleted` | إضافة ⇒ `active` أو `error`(+سبب)؛ سحب صلاحية ⇒ `revoked`؛ حذف ⇒ `deleted` |
| المسار | `draft` / `active` / `paused` | إنشاء ⇒ `draft`؛ تفعيل ناجح ⇒ `active`؛ تعطيل/حذف وجهة ⇒ `paused` |
| التسليم | `awaiting_review` / `queued` | (الإرسال والحالات اللاحقة في 7‑د) |

## 4) قاعدة البيانات (ترحيلات جديدة 0014–0016)

| الترحيل | المحتوى |
|---|---|
| `0014_publishing_bots_destinations.sql` | `publish_bots` (رمز مشفّر + بصمة + حالة)، `destinations` (chat_id فني + لقطة صلاحيات + حالة) |
| `0015_publish_routes.sql` | `publish_routes`، `route_scopes`، `routing_edges` (حواف الفحص الفني) |
| `0016_publish_deliveries.sql` | `deliveries` (+ منع التكرار)، `message_identity.publish_state`، `user_settings.delivery_retention_days` |

قيود جوهرية: `unique (identity_id, destination_id)` (D05)، `unique (user_id, chat_id)` للوجهة، `unique (user_id)` للبوت،
`check (from_chat_id <> to_chat_id)` للحواف، وشكل صريح لكل شرط مسار (`source` مقابل `rule_set`).

## 5) الواجهات الجديدة (تحت `/api/v1/telegram/publish`)

| الطريقة | المسار | الغرض |
|---|---|---|
| GET | `/status` | صحة النشر: جاهزية المفتاح، بوت، أعداد الوجهات/المسارات/التسليمات |
| GET/POST/DELETE | `/bot` · `/bot/verify` | ربط البوت/الاستبدال، إعادة التحقق، التعطيل |
| GET/POST | `/destinations` | القائمة والإضافة (بتحقق صلاحيات فوري) |
| POST | `/destinations/:id/verify` · `/pause` · `/resume` | تحقق، إيقاف، استئناف |
| DELETE | `/destinations/:id` | حذف تعطيلاً (Q15) |
| GET/POST | `/routes` | القائمة والإنشاء (مسودة) |
| PATCH/DELETE | `/routes/:id` | تعديل (بإعادة فحص لو كان فعّالاً)، حذف |
| POST | `/routes/:id/activate` · `/deactivate` | تفعيل بفحص ذري للحلقات، تعطيل |
| GET | `/deliveries?limit=` | سجل التسليمات (قراءة فقط) |

كل المسارات: مصادقة + CSRF على مستوى التطبيق + تحديد معدل + تدقيق لكل إجراء كتابي.

## 7) ملاحظات تشغيلية يجب معرفتها

1. **مفتاح جديد مطلوب:** `TG_BOT_ENC_KEY` (32 بايت base64) مستقل عن مفتاح الجلسات. بدونه:
   يظهر في الواجهة تنبيه «النشر غير مهيأ»، وتُرفض عمليات ربط البوت بـ`503 publishing_not_configured` دون أي طلب خارجي.
   التوليد: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` ثم لصقه في `apps/api/.env`.
2. **لا إرسال:** التسليمات تبقى `queued` أو `awaiting_review`. لا شيء يخرج إلى تيليجرام في هذه الدفعة.
3. **حواف التوجيه عالمية للمقارنة الفنية فقط** ولا تُعرض لأي مستخدم؛ رفض الدورة لا يذكر أي اسم لقناة أو مسار آخر.
4. **الحادثة التي وقعت وأُصلحت أثناء التطوير:** أول تشغيل لاختبارات النشر حمّل وحدة التهيئة قبل ضبط متغيّرات بيئة الاختبار،
   فكتب بيانات الاختبار في **قاعدة التطوير المحلية**. عُولج بترتيب تحميل صريح (استيراد ديناميكي بعد بدء الخادم)،
   وحُذفت بيانات الاختبار المتبقية (`*@example.test`) تحققاً بالاستعلام: `publish_bots`/`destinations`/`publish_routes`/`deliveries`/`routing_edges` = 0.
   الترحيلات 0014–0016 مطبَّقة على قاعدة التطوير أيضاً (لا أثر غير مرغوب).

## 8) خارج نطاق هذه الدفعة (7‑ج و7‑د)

- التنسيق النهائي (HTML) وتخطيط الحجب النهائي على النص المُرسل.
- تقسيم المنشور إلى أجزاء (`delivery_parts`) وحساب الطول بعد تحليل الكيانات.
- العامل، الإرسال، حدود المعدل، `retry_after`، الحالة المجهولة (O04)، الموافقة/الرفض اليدوي، والدلائل.
- حذف سجلات النشر بالاحتفاظ (العمود `delivery_retention_days` موجود، والتنظيف في 7‑د).
