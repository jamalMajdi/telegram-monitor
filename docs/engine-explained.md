# محرّك الفلترة والتصنيف وقرار النشر — شرح معماري تشغيلي

> مرجع للمدير قبل التسليم. كل رقم هنا مأخوذ من الكود الفعلي (`apps/api/src/modules/processing`,
> `.../publishing`) ومن بيانات التجربة الحيّة، لا من وصف نظري.

## الجزء الأول — دورة حياة الرسالة (١٠ بوابات)

| # | البوابة | ماذا يحدث | النتيجة إن فشلت | أين في الكود |
| --- | --- | --- | --- | --- |
| ١ | **الالتقاط** | تحديث تيليجرام ← `channel:<id>` / `chat:<id>` ← بحث عن مصدر مراقَب لنفس الحساب | محادثة غير مراقبة ⇒ عدّاد مجهول فقط، بلا صف ولا محتوى | `telegram/ingestService.ts` |
| ٢ | **الاستبعاد المتعمّد** | مصدر متوقف ⇒ `paused_source` · رسالتك أنت ومع خيار «لا تراقب رسائلي» ⇒ `self_message` | تُحتسب في عدّاد المصدر، بلا صف | الـ`ingestService` (خطوة 1) |
| ٣ | **حدود المحتوى** | نص ≤ 4096 · تعليق ≤ 1024 · مجموعهما ≤ 8192 (سقف دفاعي) — **بلا اقتطاع صامت** | `ignored / too_long` أو `no_text` | `processing/contentTypes.ts` |
| ٤ | **التطبيع** | توحيد الهمزات والتشكيل والألف/الياء والمسافات (نسخة موحّدة للاختبار فقط، لا تُخزَّن) | — | `processing/normalization.ts` |
| ٥ | **بصمة التكرار** | SHA-256 على النص المطبَّع ⇒ إن رآه المستخدم قبلًا صار `is_repeat = true` | **يُعلَّم فقط ولا يُمنع** — لا يُهمل، والقرار لك | `contentHash` + `isRepeatContent` |
| ٦ | **الفلترة (المطابقة)** | محرّك قواعد حتمي: شروط `all/any` + `minMatches` + نفي + أنماط `word/phrase/contains` + نطاق المصادر + الأولوية | لم يطابق أي فلتر ⇒ `ignored / no_filter` (أو `no_source_filter` إن لا فلتر مفعّلًا لنطاق المصدر) | `ruleEngine.ts`, `filterService.ts` |
| ٧ | **الاستخراج** | حقول (نوع الطلب، الموقع، الميزانية، الخدمة…) وجهات تواصل من النص/التعليق، **والأرقام تُقنَّع فورًا** | لا يوقف المعالجة؛ فقط قد يرفع علم المراجعة | `extraction/*` |
| ٨ | **التصنيف** | قواعد تصنيف حتمية (نفس المحرّك)؛ الترتيب: **الأولوية ← الاسم ← المعرّف**؛ عند مطابقة أكثر من تصنيف ⇒ الفائز بالأولوية + `ambiguous = true` | لا مطابقة ⇒ «غير مصنف» بثقة 0.30 | `classificationService.ts` |
| ٩ | **القالب** | الترتيب: مسار النشر ← المصدر ← الفلتر ← التصنيف ← الافتراضي | بلا قالب ⇒ لا نشر (يبقى في النتائج) | `templateResolver.ts` |
| ١٠ | **التوجيه ثم التسليم** | مسار فعّال يغطي المصدر ⇒ تسليم واحد **لكل وجهة**؛ ثم العامل يرسله: 2xx ⇒ `published`، 5xx/شبكة ⇒ `uncertain` بلا إعادة تلقائية | بلا مسار ⇒ `not_routed` | `publishing/routingService.ts`, `deliveryWorker.ts` |

قبل كل ذلك وبعده: **منع الحلقات** (لا حافة تُغلق دورة مصدر↔وجهة)، **وحدّ التكرار**، **والاحتفاظ** (نص الرسالة يُمسح بانتهاء مدته، والهوية/الأرقام بعد 30 يومًا، والعدّادات تبقى).

## الجزء الثاني — عتبة الثقة: كيف يُتَّخذ القرار بالضبط

> **أهم تصحيح ذهني:** لا يوجد نموذج ذكاء اصطناعي ولا «نسبة ذكاء». الثقة **رقم محسوب بقاعدة معلنة**، وقرار المراجعة **مجموع ثلاث بوابات** لا واحدة.

### ٢-١ صيغة الثقة (الكود كما هو)

```
confidence = 0.6 + 0.1 × min(2, عدد الشروط المحقَّقة) − (0.1 إن وُجد تصنيف منافس)
ثم تُقيَّد النتيجة بين 0.35 و 0.90
```

| الحالة | الثقة | التفسير |
| --- | --- | --- |
| شرط واحد محقَّق، بلا منافس | **0.70** | رسالة الواجبات في تجربتنا |
| شرطان محقَّقان، بلا منافس | **0.80** | رسالة العقارات في تجربتنا (شرطان: «للإيجار» + كلمة نوع) |
| شرط واحد + تصنيف منافس | **0.60** | تنجو من عتبة الثقة لكن **توقفها بوابة الغموض** |
| لا شرط (تصنيف «غير مصنف») | **0.30** | ليست تصنيفًا حقيقيًا |

### ٢-٢ بوابات المراجعة الثلاث (كل واحدة تكفي للوقف)

```ts
needsReview =
     استخراج غير مؤكد        // أي حقل أو رقم تواصل: ambiguous = true أو confidence < 0.60
  || تصنيف غامض             // ambiguous = true (أي مطابقة تصنيف ثانية)
  || ثقة التصنيف < 0.60     // الحد الفاصل حصريًا: 0.60 تمرّ، 0.59 تقف
```

**ثم تُضاف بوابة رابعة على مستوى المسار**: إن كان `publishMode = 'review'` في المسار ⇒ وقف دائمًا.
ويُسجَّل **سبب الوقف** بدقة: `message` (من الرسالة نفسها) أو `route` (طلب المسار).

### ٢-٣ لماذا توقّفت رسالة الواجبات وتُشرت رسالة العقارات؟

| البند | رسالة العقارات (نُشرت) | رسالة الواجبات (وُقفت) |
| --- | --- | --- |
| الفلاتر المطابقة | «عقارات» + فلترك المخصّص (فلترة = نعم) | «واجبات واختبارات» + «مشاريع جامعية» |
| التصنيف الفائز | عقارات · **0.80** | واجبات واختبارات · **0.70** |
| تصنيف منافس؟ | **لا** | **نعم** («مشاريع جامعية») ⇒ `ambiguous = true` |
| الاستخراج | حقل 0.67 · هاتف 0.75 ⇒ سليم | حقول: لا شيء · هاتف 0.80 ⇒ سليم |
| **القرار** | لا بوابة تحفّز ⇒ **تلقائي** | بوابة الغموض ⇒ **`awaiting_review` / السبب `message`** |

**✅ إصلاح نُفِّذ أثناء هذا الشرح:** كانت واجهة التفاصيل تعرض `ambiguous: false` **ثابتة** رغم أن القاعدة
تحمل `true` — أي أن النظام أوقف الرسالة لسببٍ لم يعرضه للمستخدم. صُحّح الآن:
`ambiguous` يُقرأ من القاعدة، وأُضيفت قائمة **`reviewHints`** تُعرض في صفحة الرسالة تحت عنوان
**«لماذا أوقف النظام هذه الرسالة؟»**، مشتقّة من **نفس** شروط القرار (لا أسباب مخترعة ولا مخفيّة).

## الجزء الثالث — ما يمكنك التحكم به كمدير (وأين)

| الكيان | عبر الواجهة (V1) | عبر الأداة `tg-cli` (مضاف الآن) | ملاحظة |
| --- | --- | --- | --- |
| **الفلاتر**: كلمات، نمط، نفي، أولوية، نطاق، اختبار فوري | ✅ **شاشة كاملة** `/telegram/filters` (أُضيفت بعد الشرح الأول) | ✅ كامل | الاختبار **في الذاكرة بلا حفظ ولا كتابة في القاعدة** |
| **القواميس** (مصطلحات مشتركة تُضاف لشروط) | ❌ | ✅ `dictionaries list` (الإنشاء عبر API) | القواميس المبذورة: صيغ الطلب، مهن وخدمات، مصطلحات دراسية/عقارية/بيع وشراء |
| **التصنيفات** (قواعد + أولوية + إيقاف + حذف) | ✅ **شاشة كاملة** `/telegram/classifications` (أُضيفت بعد الشرح الأول) | ✅ إنشاء/تعديل/حذف | التعديل يرفع إصدار الإعدادات فوراً ويُسجّل في التدقيق |
| **القوالب** ونصوصها والافتراضي | 👁️ عرض + تعيين الافتراضي | 👁️ `templates list` | **قيد V1**: تحرير نصوص القوالب غير مكشوف |
| **المسارات**: الوضع `auto/review`, سياسة الطول, النطاق, التفعيل | ✅ كامل (صفحة «النشر إلى تيليجرام») | — | هذا هو المفتاح الذي تحوّل به «هدف المراجعة» إلى «نشر تلقائي» |
| **المراجعة الفردية**: اعتماد/رفض/تغيير التصنيف/تمييز كمُراجَع | ✅ كامل (صفحة النتائج ← تفاصيل الرسالة) | — | القرار اليدوي يعلو على الآلي ويُسجَّل في التدقيق |

### تحديث معماري: الدمج نُفِّذ فعلاً
دُمجت التصنيفات الأربعة المتقاربة («طلبات المساعدة الدراسية»، «واجبات واختبارات»، «مشاريع جامعية»،
«خدمات») في تصنيف واحد **«خدمات طلابية»** (الترحيل `0026`)، ونُقلت إليه نتائج التصنيف وروابط القوالب.
النتيجة: لا يمكن أن تتطابق تصنيفان دراسيان مع الرسالة نفسها ⇒ **يصبح `ambiguous = false`** وتُنشر تلقائياً.

### وصفة عملية: «خدمات أكاديمية» تُنشر تلقائيًا بلا مراجعتي

السبب الجذري للوقوف ليس الكلمات المفتاحية بل **تعارض تصنيفين**. ثلاث طرق مرتبة من الأسرع:

1. **الاعتماد اليدوي مرة واحدة** (فوري، بلا إعداد): صفحة النتائج ← الرسالة ← «اعتماد»؛ القرار اليدوي يصبح هويّة هذه الرسالة ويُبقيها مُصنَّفة.
2. **فلتر مخصّص عالي الأولوية** (الأسرع للإعداد المستمر) — يضمن المطابقة لكنه لا يزيل الغموض وحده:
   ```bash
   node scripts/tg-cli.mjs filters create \
     --name "خدمات أكاديمية" --priority 20 \
     --terms "حل الواجبات,حل الكويزات,تلخيص,بحث تخرج,مشروع تخرج,ميد,فاينل" \
     --match-mode phrase
   node scripts/tg-cli.mjs filters bind <id> --sources <sourceId>
   ```
3. **إزالة التعارض في قواعد التصنيف** (الحل الجذري، يتطلب تعديل قواعد التصنيف — قيد V1 أنه غير مكشوف في الواجهة):
   اجعل شرط «واجبات واختبارات» أضيق (شرطان: `all` + `minMatches`) أو أضف نفيًا لتصنيف «مشاريع جامعية»
   بكلمة «واجبات»، فيبقى تصنيف واحد ⇒ `ambiguous = false` ⇒ نشر تلقائي.

> **قاعدة ذهبية:** الفلتر يجيب «هل تهمّني هذه الرسالة؟» والتصنيف يجيب «ما نوعها؟». الرسالة تُنشر
> إذا أجابت الأولى بنعم، والثانية **بلا منافس وثقة ≥ 0.60**، ولم يطلب المسار مراجعة.

## حارس المحتوى: لماذا لا يُنشر قالب فارغ

القالب يجيب: «بأي شكل أُخرج الرسالة؟» والاستخراج مقيَّد بالقرائن، فقد لا يجد أي قيمة (رسالة عامية بلا
«الموقع:» أو «السعر:»). في هذه الحالة:

1. **`buildLines`** لا يعتبر العنوان والفاصل محتوىً؛ بلا سِطر محتوى ⇒ `empty` (رفض بنيوي).
2. **`assembleSource`** يعرض **النص الأصلي** في أول حقل حرّ («التفاصيل») ⇒ منشور حقيقي بدل هيكل فارغ.
3. بلا نص أصلي (احتفاظ منتهٍ/وسائط) ⇒ `blocked/empty` بلا إرسال.

وهذا يفسّر أيضاً دور القواميس: هي تُحسّن **المطابقة والتصنيف** (اختيار القالب الصحيح)، بينما **الاستخراج**
لا يخترع قيماً بلا قرائن — لذلك الحارس ضروري لا تجميلي.

المعجم المبذور: 8 قواميس، أكثر من 1000 مصطلح، منفصلة حسب النطاق، مع قاموس «مفردات النطاقات المتخصصة»
الذي يجعل «طلبات عامة» احتياطاً فعلياً لا منافساً (سبب سابق لحجز رسائل سليمة للمراجعة).
