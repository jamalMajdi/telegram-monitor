# مراجعة تقنية — الخطوة الثالثة (إدارة مصادر تيليجرام)

**التاريخ:** 2026‑11‑24 · **النطاق:** مراجعة كود وتشغيل اختبارات فقط. لم تُضف ميزات، ولم تبدأ الخطوة الرابعة،
ولم يُطبَّق أي تغيير مخطط جديد (المقترح في §1 ينتظر إقراراً).

## 1) عزل الملكية على مستوى قاعدة البيانات

### ما تحققت منه مباشرة
- `0006_telegram_sources.sql`: `user_id` → `users(id)` و`account_id` → `telegram_accounts(id)`، وكلاهما `on delete cascade`،
  مع فهارس `(user_id, created_at desc)` و`(account_id, status)`، وقيد فريد `(user_id, peer_type, peer_id)`.
- **لا يوجد أي قيد يضمن أن `telegram_sources.user_id` يساوي `telegram_accounts.user_id`** — الربط يفحصه
  `requireOwnedAccount()`/`requireAddableAccount()` في الخدمة فقط.
- **فحص تجريبي (probe) على قاعدة التطوير**: إدراج صف بـ`user_id = B` و`account_id` يملكه `A` **نجح** ثم حُذف
  (النتيجة: `INSERTED (لا يوجد ضمان في قاعدة البيانات)`, والباقي بعد التنظيف = 0). أي أن الضمان خدمي فعلاً.
- المسارات كلها تمرّ بالخدمة: `requireOwned` لمصادر الغير تُعيد 404 (مُختبر في 7 عمليات + إضافة لحساب الغريب).
- `findOwned`, `listByUser` تُقيّد بـ`user_id`؛ `setStatus/setIncludeOwnMessages/recordVerification/delete` تُستدعى بعد
  فحص الملكية، ومعرّف المصدر لا ينتقل بين المستخدمين (لا مسار لتغيير `user_id`) فسباق TOCTOU غير عملي هنا.

### المخاطر
1. أي كتابة مستقبلية خارج الخدمة (عامل قراءة، سكربت إداري، تحويل حساب بين مستخدمين) قد تُنشئ مصدراً متقاطع الملكية،
   وحينها تظهر بيانات مستخدم داخل قائمة آخر (قراءة العنوان/الاسم فقط اليوم، لكنها ثغرة عزل بنيوية).
2. حذف مستخدم لا يحذف حساباته تلقائياً (الحسابات تُحذف فقط عبر `revoked`)، فلا خطر حذف متسلسل غير مقصود هنا.

### أقوى حماية مقترحة (تنتظر إقرارك — لم تُطبَّق)
مفتاح أجنبي مركّب يجعل القاعدة نفسها ترفض التقاطع، دون أي تغيير معماري ولا تعديل 0006 (ترحيل جديد `0007`):

```sql
-- 0007_source_owner_integrity.sql (مقترح)
alter table telegram_accounts
  add constraint telegram_accounts_id_user_key unique (id, user_id);

alter table telegram_sources
  drop constraint telegram_sources_account_id_fkey;      -- يُستبدل بالمفتاح المركّب

alter table telegram_sources
  add constraint telegram_sources_account_owner_fkey
  foreign key (account_id, user_id)
  references telegram_accounts (id, user_id)
  on delete cascade;

-- تصحيح تعليق قديم: الفترات تُحذف فعلاً عند حذف المصدر (cascade)
comment on table telegram_source_periods is
  'فترات تفعيل المصدر: تُفتح عند الإضافة/الاستئناف وتُغلق عند الإيقاف أو الفصل؛ تُحذف مع المصدر،
   وتبقى آثارها في audit_events.';
```
- **تم التحقق من صلاحيته**: نُفِّذ داخل معاملة أُلغيت (rollback) على قاعدة التطوير ونجح التعريف بالكامل.
- التكلفة: فهرس فريد إضافي على `telegram_accounts` (جدول صغير) + مفتاح أجنبي مركّب؛ لا تغيير في الأعمدة ولا في العقود
  ولا في سلوك الحذف المتسلسل (S9).
- **لم أطبّقه** لأنه يعدّل مخططاً معتمداً في 0006، وقرارك بالمراجعة كان «اقترح».

### صورة الوضع الحالي
| الطبقة | الضمان |
|---|---|
| HTTP | مصادقة + ملكية (404 للغير) ✅ |
| الخدمة | `findOwned`/`requireOwnedAccount` قبل كل عملية ✅ |
| المستودع | استعلامات مقيّدة بـ`user_id` للقراءة؛ التعديل بالمعرّف بعد فحص ✅ |
| قاعدة البيانات | الملكية بين الجدولين **غير مضمونة** ⚠️ (مقترح أعلاه) |

## 2) دقة معرّفات تيليجرام (BIGINT)

| المرحلة | التنفيذ | النتيجة |
|---|---|---|
| قراءة من المكتبة | `mapEntityToSource`/`describeResolvedSource` تستخدم `String(entity.id)` | ✅ لا تحويل إلى `Number` |
| تحليل المُدخل | `parseSourceIdentifier` يعيد **نصاً**، و`getEntity(BigInt(...))` | ✅ |
| التحقق في HTTP | `peerIdSchema`: `^\d{1,19}$` + حد `9223372036854775807` | ✅ (أُضيف في هذه المراجعة) |
| التحقق في الخدمة | `/^\d{1,19}$/` + `BigInt(peerId) <= BIGINT_MAX` | ✅ (أُضيف) |
| التخزين | `insert … $4::bigint` بقيمة نصية | ✅ |
| القراءة من DB | `peer_id::text as peer_id` في كل الاستعلامات | ✅ |
| استجابة API | `peerId: string` في `SourceView`/`AvailableSourceView` | ✅ (مُختبر: `typeof === 'string'`) |
| الواجهة | `peerId: string` في الأنواع، ويُرسل نصاً كما هو | ✅ |
| اختبار دقة | إضافة `9007199254740993` (2⁵³+1) ومقارنة النص في API وDB والقائمة | ✅ يطابق تماماً |
| `messageMapper` | `Number(message.id)` لمعرّف الرسالة (≤31 بت)، و`String(channelId)` لمفتاح الند | ✅ لا يمسّ `peer_id` |

**مشكلتان اكتُشفتا وأُصلحتا:**
1. `peerId` مكوَّن من 20 رقماً (أكبر من BIGINT) كان يمرّ إلى قاعدة البيانات ثم يفشل بـ500؛ صار يُرفض بـ`400 validation_error`
   في طبقة HTTP (وفي الخدمة كخط دفاع ثانٍ).
2. `parseSourceIdentifier` كان يقبل المعرّفات **السالبة** (`^-?\d{5,20}$`) فتصل إلى `getEntity`؛ صار يرفضها كـ`unsupported`
   → `400 unsupported_source_type`، ولم يبقَ أي مسار يصل إلى قيد `peer_id > 0` بخطأ قاعدة بيانات.

## 3) سلامة فترات المراقبة

- **الإضافة**: `insert` + فتح فترة `activated` داخل معاملة واحدة؛ فشل الإدراج (تكرار) يترك صفر فترات (مُختبر).
- **الإيقاف**: `select … for update` ثم إغلاق الفترة المفتوحة (`ended_at`, `reason`) في نفس المعاملة.
- **الاستئناف**: نفس القفل، ثم فتح فترة واحدة فقط عند تغيّر الحالة (لا فترة عند الاستئناف المتكرر — مُختبر).
- **الفصل**: `pauseForAccount` يمرّ بنفس `setStatus` لكل مصدر نشط ← تُغلق الفترة ويبقى الصف ظاهراً (مُختبر).
- **الحذف**: صف المصدر يُحذف وفتراته معه (`cascade`)؛ لا فترات يتيمة (مُختبر بعد سباق إضافة).
- **عدم وجود فترتين مفتوحتين**: مفروض بفهرس فريد جزئي `(source_id) where ended_at is null`، إضافةً إلى القفل الصفّي.
- **التزامن (مُختبر الآن)**: إيقاف متزامن ×2 → فترة واحدة مغلقة؛ استئناف متزامن ×2 → فترتان إجمالاً واحدة مفتوحة؛
  فحص عام على كل القاعدة: صفر مصادر بفترتين مفتوحتين؛ إضافة مكررة متزامنة → `201` + `409` وصف واحد فقط.
- **ملاحظة (ليست عطلاً)**: `resume` لا يطلب اتصالاً فعلياً بالحساب (يكفي ألا يكون `revoked/suspended`)؛ الحالة تعبّر عن
  نيّة المراقبة، والاتصال شأن تشغيلي. موثّق ضمن القيود.

## 7) نقاط تحتاج قراراً إضافياً

1. **تطبيق `0007`** (المفتاح الأجنبي المركّب للملكية + تصحيح تعليق الفترات) — جاهز ومُختبَر تعريفياً، ينتظر موافقتك.
2. **أثر جانبي محتمل** لو طُبِّق 0007: أي صف قديم متقاطع الملكية سيمنع إنشاء القيد. الفحص الحالي على قاعدة التطوير:
   `mismatched = 0` من إجمالي **0 صفوف** (لا مصادر بعد في قاعدة التطوير) — أي أن الفحص نظيف لكنه غير مُثبت على بيانات فعلية.
3. **هل `resume` يجب أن يشترط اتصالاً فعلياً** مثل الإضافة؟ الآن لا يشترطه (يكفي ألا يكون الحساب `revoked/suspended`).
4. **ذرّية إيقاف مصادر الحساب المفصول**: حالياً مصدر بمصدر. هل نريده في معاملة واحدة (كل شيء أو لا شيء)؟
5. **حد المصادر** يُحسب شاملًا الموقوفة، ولكل حساب؛ هل نستثني الموقوفة من العدّ؟

# 9) تنفيذ قرارات المراجعة النهائية (2026‑11‑24)

اعتمد المستخدم القرارات في §7، ونُفِّذ منها ما يلي **حصراً** (بلا ميزات إضافية ولا عمل على الخطوة الرابعة).

## 9.1 الترحيل `0007_source_owner_integrity.sql`

```sql
-- فحص مسبق: يتوقف الترحيل بخطأ واضح إن وُجد صف متقاطع الملكية (بلا تعديل بيانات)
do $$ ... raise exception 'يوجد % صفاً ...' ... $$;

alter table telegram_accounts
  add constraint telegram_accounts_id_user_key unique (id, user_id);

alter table telegram_sources drop constraint telegram_sources_account_id_fkey;

alter table telegram_sources
  add constraint telegram_sources_account_owner_fkey
  foreign key (account_id, user_id) references telegram_accounts (id, user_id)
  on delete cascade;

comment on table telegram_source_periods is '... تُحذف مع المصدر (cascade) ...';
```

- **الفحص المسبق قبل التطبيق** (قاعدة التطوير): `mismatched = 0` من إجمالي **0 صفاً** → لا سجلات متقاطعة، فطُبِّق الترحيل.
- **بعد التطبيق** (قراءة من `pg_constraint`):
  `telegram_sources_account_owner_fkey => FOREIGN KEY (account_id, user_id) REFERENCES telegram_accounts(id, user_id) ON DELETE CASCADE`
  و`telegram_accounts_id_user_key => UNIQUE (id, user_id)`، والمفتاح الأحادي القديم **غير موجود**.
- `on delete cascade` محفوظ على المفتاح الجديد (S9).
- الترحيل يسبقه فحص ذاتي: أي قاعدة فيها صف متقاطع تُوقف الترحيل برسالة صريحة ولا تُعدَّل بياناتها.

## 9.2 ذرّية فصل الحساب

**التصميم:** قطع اتصال تيليجرام (عمل شبكي غير قابل للتراجع) يحدث **أولاً**، ثم كل تغييرات قاعدة البيانات في
**معاملة واحدة**: `closeAll(challenges)` → `deleteTelegramSession` → `markRevoked` → `pauseForAccount` (إغلاق الفترات ثم
`paused`) → `recordAudit`. أي فشل ⇒ `rollback` كامل ورفع الخطأ (500).

**ما تغيّر تقنياً:**
| الملف | التغيير |
|---|---|
| `sessionStore.ts` | `deleteTelegramSession(accountId, userId, client?)` — تُنفَّذ داخل منفّذ المعاملة |
| `accountRepository.ts` | `markRevoked(accountId, client?)` و`deleteSession(..., client?)` |
| `loginChallengeStore.ts` | `closeAll(accountId, client?)` |
| `sourceRepository.ts` | `pauseForAccount(accountId, reason, client?)` → `pauseForAccountWith` بجملتين (إغلاق الفترات ثم تحديث الحالة) داخل منفّذ واحد، والنسخة المستقلة تلتف في `withTransaction` |
| `loginService.ts` | `unlinkAccount` صار يستخدم `withTransaction` ويضمّ التدقيق داخل المعاملة، وبلا `.catch()` يبتلع الفشل |

**السلوك محفوظ:** الحساب يبقى بسجل `revoked`، والمصادر تبقى ظاهرة بحالة `paused`، وفتراتها مغلقة لا محذوفة.

## 9.3 اختبار الملكية على مستوى قاعدة البيانات

اختبار جديد: `تمنع قاعدة البيانات ربط مصدر بحساب يملكه مستخدم آخر`
- إدراج مباشر بـ`user_id = مستخدم آخر` مع `account_id` لذلك المستخدم ⇒ **مرفوض `23503`**.
- محاولة نقل مصدر قائم إلى مستخدم آخر بـ`update … set user_id` ⇒ **مرفوض `23503`**.
- المسار المشروع يعمل، والمستخدم الآخر يرى قائمة فارغة و`404` على المصدر.

## 9.4 اختبار ذرّية الفصل

اختبار جديد: `يُفصل الحساب ذرّياً: فشل إيقاف مصدر لا يترك أي تغيير جزئي`
1. مستخدم + حساب مرتبط + مصدرَان (أحدهما `title = 'BLOCK_PAUSE'`) + جلسة مشفّرة واحدة.
2. لقطة قبل: `{ account: active, sources: 2 active / 0 paused, openPeriods: 2, sessions: 1 }`.
3. حقن فشل: trigger على `telegram_sources` يرفع استثناء عند إيقاف ذلك المصدر — ويُتحقق أولاً أن الاستثناء نفسه يحدث.
4. `DELETE /api/v1/telegram/accounts/:id` ⇒ **500**، واللقطة **مطابقة تماماً** لما قبل (لا `revoked`، لا مصدر متوقف،
   لا فترة مغلقة، لا حذف جلسة، لا حدث تدقيق).
5. بعد إزالة سبب الفشل: `204`، واللقطة `{ revoked, 0 active / 2 paused, openPeriods: 0, sessions: 0 }`،
   وفترتان محفوظتان مغلقتان، وحدث تدقيق واحد فقط.
