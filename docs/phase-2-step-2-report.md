# تقرير المرحلة الثانية — الخطوة الثانية: ربط حسابات تيليجرام وإدارة الجلسات

**الحالة:** منفّذ داخل مساحة العمل، مع 16 اختبار تكامل جديد + 5 اختبارات وحدة + اختبار تسريب سجلات.
**حدود الإثبات:** كل اختبارات الربط تعمل على قاعدة PostgreSQL حقيقية مع **بوابة تيليجرام محاكاة**. لم يُجرَ أي
تسجيل دخول حقيقي، ولم يُستخدم أي رمز أو كلمة مرور حقيقية، ولم تُغيَّر أي بيانات اعتماد.

## 1) ما تم تنفيذه فعلياً
1. ربط حساب برقم الهاتف عبر MTProto: `auth.sendCode` ثم `auth.SignIn` ثم — عند الحاجة — `auth.GetPassword` +
   `computeCheck` (SRP) + `auth.CheckPassword`، بثلاث خطوات HTTP صريحة وليست جلسة تفاعلية واحدة.
2. حالة مصادقة مؤقتة في الخادم (قاعدة البيانات) مشفّرة وبصلاحية زمنية وعدّادات محاولات.
3. حفظ الجلسة بعد النجاح عبر Session Cipher الحالي + تحديث هوية الحساب + استهلاك المحاولة.
4. إدارة الاتصال عبر Connection Manager الحالي: توصيل بعد الربط، توصيل/فصل يدوي، استعادة تلقائية عند بدء الخادم.
5. عرض الحسابات وحالة الاتصال، إعادة المصادقة، إلغاء المحاولة، الفصل النهائي مع حذف الجلسة.
6. واجهة React كاملة (صفحة `/telegram`) مبنية على مكوّنات المشروع الحالية ونظام الجلسة/CSRF نفسه.
7. منع التكرار: محاولة نشطة واحدة لكل حساب، اتصال واحد لكل حساب، وحساب واحد لكل (مستخدم، رقم غير مفصول).

## 3) التعديلات على قاعدة البيانات (الترحيل 0005)
- `telegram_accounts.phone_hash` (بصمة HMAC-SHA256) + قيد صيغة + **فهرس فريد جزئي** `(user_id, phone_hash)`
  حيث `status <> 'revoked'`: يمنع ربط الرقم نفسه مرتين، ويسمح بإعادة الربط بعد الفصل.
- `telegram_login_challenges`: `stage` (code/password)، `ciphertext` (مغلّف AES-256-GCM)، `key_version`،
  `code_attempts`, `password_attempts`, `resend_count`, `last_sent_at`, `expires_at`, `consumed_at`.
  قيود: طول مغلّف أدنى، نسخة مفتاح ≥ 1، عدّادات غير سالبة، `expires_at > created_at`،
  و**فهرس فريد جزئي** على `account_id where consumed_at is null` (محاولة نشطة واحدة لكل حساب).
- لا يوجد أي عمود لرمز التحقق أو كلمة المرور؛ ولا يُحفظ الرقم الكامل (بصمة + آخر رقمان فقط).

## 4) طريقة الربط وإدارة المصادقة
| الخطوة | المسار | المكتبة |
|---|---|---|
| بدء | `POST /api/v1/telegram/accounts` | `auth.sendCode` (عبر `sendCode` من `teleproto/client/auth`) |
| إعادة إرسال | `POST /api/v1/telegram/accounts/:id/code` | `auth.sendCode` مرة أخرى بحدود |
| إدخال الرمز | `POST /api/v1/telegram/accounts/:id/verify` | `auth.SignIn` |
| تحقق بخطوتين | `POST /api/v1/telegram/accounts/:id/password` | `auth.GetPassword` + `computeCheck` + `auth.CheckPassword` |
| إعادة مصادقة | `POST /api/v1/telegram/accounts/:id/reauth` | نفس تدفق البدء لحساب قائم |
| إلغاء | `POST /api/v1/telegram/accounts/:id/cancel` | — (يُغلق المحاولة ويُحذف السجل المعلّق) |
| توصيل/فصل | `POST /api/v1/telegram/accounts/:id/connect|disconnect` | Connection Manager |
| فصل نهائي | `DELETE /api/v1/telegram/accounts/:id` | حذف الجلسة + `status = revoked` |

الحالة المؤقتة: مهلة 10 دقائق (قابلة للضبط)، 5 محاولات رمز، 3 محاولات كلمة مرور، 3 مرات إعادة إرسال بفاصل 30 ثانية،
وحد معدل HTTP مستقل لكل مستخدم على كل مسار. كل خطوة محمية بقفل لكل حساب فلا تتنفّذ خطوتان متوازيتان على المحاولة نفسها.

## 5) حفظ الجلسات وتشفيرها واستعادتها
- بعد المصادقة: تُقرأ الجلسة من عميل المكتبة وتُحفظ بـ `saveTelegramSession` (AES-256-GCM، AAD `tg-session:v1:<accountId>:<keyVersion>`)
  مع حالة التحديثات؛ ثم تُستهلك المحاولة وتُحذف جلسة الربط المؤقتة من الذاكرة.
- الاستعادة: `manager.connect` يقرأ الجلسة المشفّرة ويفكّها ويمرّرها إلى العميل الجديد؛ لا تُنشأ جلستان لحساب واحد.
- عند بدء الخادم: `TG_RESTORE_ON_START=true` يعيد توصيل الحسابات النشطة التي لها جلسة (بثلاث عمليات متوازية كحد أقصى)،
  وقد نُفِّذ فعلياً على قاعدة التطوير: `attempted=0` (لا حسابات مرتبطة بعد) بلا أي اتصال خارجي.
- الجلسة المؤقتة قبل المصادقة تُحفظ أيضاً داخل مغلّف بغرض `login` (AAD مختلف)، ليستمر التدفق بعد إعادة تشغيل الخادم.

## 6) عزل المستخدمين وحماية البيانات
- كل استعلام في مخزن الجلسات/الحسابات مقيّد بـ `user_id`؛ الملكية تُتحقق قبل كل قراءة/تعديل/حذف.
- اختبار صريح: مستخدم آخر يحصل على 404 على العرض والتحقق وكلمة المرور والتوصيل والحذف، وقائمته فارغة.
- المسارات كلها تتطلب جلسة مستخدم مصادقاً عليه (`requireAuth`) وتمرّ بحماية CSRF القائمة.
- الاستجابة لا تحتوي أي حقل جلسة أو بصمة رمز أو رقم كامل؛ ولا `telegram_user_id` الداخلي.
- اختبار آلي يثبت خلو السجل من الرقم والرمز وكلمة المرور والجلسة أثناء ربط كامل ثم فصل.

## 8) المشكلات التي ظهرت وكيف عولجت
1. **استيراد `computeCheck`**: لا يوجد تصدير باسم `Password` في خريطة الحزم؛ استُخدم `teleproto/Password` بعد التحقق من
   وجوده فعلياً في الإصدار المثبّت.
2. **نوع `auth.SignIn`**: النتيجة اتحاد يضم `authorizationSignUpRequired` (رقم غير مسجّل)؛ أُضيف استخراج صريح
   ورفض واضح بدل الافتراض.
3. **الرقم غير المطبَّع**: أول تنفيذ كان يبني البصمة دون تطبيع؛ أُضيف `normalizePhoneNumber` يجب أن يسبق كل شيء،
   ويُعيد خطأ تحقق عربياً بدل رمي استثناء داخلي (اختبار «يرفض أرقام الهاتف غير الصالحة»).
4. **قيد `expires_at > created_at`**: منع اختبار «انتهاء الصلاحية» من تزوير التاريخ للخلف؛ صُحّح الاختبار بتعديل
   `created_at` أيضاً مع الحفاظ على القيد (القيد نفسه مفيد للإنتاج).
5. **محاكاة فاشلة الاتصال**: تمرير كائن خطأ كأنه نتيجة اتصال جعل الحالة `needs_reauth` بدل إعادة المحاولة؛
   أُضيف `queueFailure` ليُرمى الخطأ فعلياً من المحاكاة.
6. **تعارض كتابة الهوية**: المحاكاة كانت تعيد هوية مختلفة عند الاتصال فتطمس هوية الربط؛ صُحّح بجعل الهوية
   قابلة للضبط في المحاكاة (واقعياً هي الهوية نفسها).
7. **اختبار السجلات**: كان يتوقع رموز التدقيق في ملف السجل، والتدقيق يُكتب في القاعدة؛ صُحّح ليتحقق من سجلات
   الطلبات مع بقاء فحص الأسرار.
8. **عدّ الترحيلات في المرحلة الأولى**: ارتفع إلى 5؛ حُدَّث الاختبار (35/35 ناجح بعد التعديل).

## 9) متطلبات وقرارات تحتاج موافقتك
1. **تسجيل الدخول عبر البريد (FIRE)**: يُرفض حالياً برسالة `unsupported_delivery`. أي دعم يحتاج قراراً (خطوة إضافية).
2. **PHONE_MIGRATE**: لم يُنفَّذ ترحيل تلقائي بين مراكز البيانات؛ يظهر كخطأ تشغيلي. أنصح بإضافته في خطوة تالية
   بعد اختبار حي حقيقي.
3. **إعادة المصادقة تتطلب إدخال الرقم من جديد** لأننا لا نخزّن الرقم الكامل (قرار خصوصية متوافق مع §3.3). البديل
   (تخزين الرقم مشفّراً) قرار معماري يحتاج موافقتك.
4. **لا حد لعدد الحسابات لكل مستخدم** (`§3.2`: حساب واحد افتراضياً + إمكانية إضافة أخرى)؛ لم أفرض سقفاً غير منصوص.
5. **الفصل = سجل تاريخي (`revoked`) وليس حذفاً كاملاً**، مع مسح الهوية والبصمة والجلسة. إن رغبت بحذف كامل للسجل فوراً
   فالقرار لك.
6. **حد المعدل ما زال في الذاكرة** لكل عملية خادم (كما في المرحلة الأولى)؛ التوسع الأفقي يحتاج مخزناً مشتركاً.
7. **الاختبار الحي للربط** ما زال غير منفّذ: يحتاج تشغيلك للتسجيل من واجهة `/telegram` أو الأداة، وإبلاغي بالنتيجة
   دون إرسال أي رمز أو كلمة مرور.

## 10) كيفية التشغيل والتحقق لاحقاً
```bash
# قاعدة البيانات والترحيلات
cd telegram-monitor && npm run dev:db          # طرفية أولى
npm run migrate                                # يطبّق 0005

# الخادم والواجهة
npm run dev:api                                # http://localhost:4000
npm run dev:web                                # http://localhost:5173

# في الواجهة: تسجيل الدخول → «حسابات تيليجرام» → أدخل الرقم → الرمز → (كلمة تحقق ثانية عند الحاجة)
# ثم: توصيل/فصل، إعادة المصادقة، أو «فصل الحساب وإلغاء الربط».

# فحص سريع بلا واجهة (يتطلب ملف جلسة المتصفح):
curl -s http://localhost:4000/api/v1/telegram/status

# الاختبارات
cd apps/api && npm test        # 100 ناجحاً + 4 حيّة متجاوزة
```
**ما ثبت فعلاً:** التدفق الكامل على مستوى الـ API والواجهة مع قاعدة بيانات حقيقية، التشفير والعزل، الحدود
والمهل، ومنع التكرار، وعدم تسريب الأسرار في السجلات.
**ما بقي بحاجة لاختبار حي:** التسجيل الفعلي برمز حقيقي، التحقق بخطوتين الحقيقي، سلوك أخطاء تيليجرام الحقيقية
(FLOOD_WAIT/PHONE_MIGRATE)، واستعادة الاتصالات بعد إعادة تشغيل حقيقية مع حساب مرتبط.
