# المرحلة 4 — الدفعتان P4‑أ وP4‑ب: تقرير التنفيذ

> نطاق هذه الدفعة كما اتُّفق: **P4‑أ** = نموذج القراءة + لوحة المستخدم، و**P4‑ب** = التشغيل
> (نبض العامل، الجهوزية، المقاييس). التوقف هنا مقصود؛ الدفعات P4‑ج…P4‑ز لم تبدأ.

## 1) ما نُفِّذ

### P4‑أ — نموذج القراءة ولوحة المستخدم (§12.1، Q16, Q20, Q24, Q30)

| المكوّن | الملف | الوصف |
| --- | --- | --- |
| مستودع العدّادات | `apps/api/src/modules/dashboard/dashboardRepository.ts` | استعلام واحد متعدد الـCTE ينتج ٢٣ عدّاداً مقسّمة على سبع مجموعات (تيليجرام، المصادر، الفلاتر، القوالب، الوجهات، الرسائل، التسليمات). كل فرع مقيَّد بالمالك: `user_id` مباشرةً، أو عبر `message_identity` لأن `message_matches` لا يحمل `user_id`. |
| خدمة اللوحة | `dashboard/dashboardService.ts` | ذاكرة قصيرة ١٥ ثانية لكل مستخدم + `invalidate()`، وسقف للنشاط (≤50)، ودالة تنبيهات نقية `buildAlerts()`. |
| المسارات | `dashboard/dashboardRoutes.ts` | `GET /api/v1/dashboard/summary?fresh=1` و`GET /api/v1/dashboard/activity?limit=1..50` (كلاهما خلف الجلسة، ولا يقرأ إلا صفوف صاحب الطلب). |
| الواجهة | `apps/web/src/pages/DashboardPage.tsx` | بطاقات حالة + شريط تنبيهات بروابط إصلاح مباشرة + «آخر العمليات» + صندوق حدود النظام. عربية RTL، بلا أي نص رسالة أو قيمة تواصل. |
| عميل الواجهة | `apps/web/src/api/client.ts` | أنواع `DashboardSummary`/`DashboardAlert`/`DashboardActivityItem` و`dashboardApi`. |

**سلوك التنبيهات** (مشتقّة من العدّادات فقط، لا تُخترع): `needs_reauth` حرج، `uncertain_delivery` حرج،
`awaiting_review` تحذير، `no_source`/`no_destination` معلومة — مع ترتيب يحفظ الخطورة أولاً.

### P4‑ب — التشغيل والنبض والمقاييس (Q17, Q18, Q26, Q29)

| المكوّن | الملف | الوصف |
| --- | --- | --- |
| مستودع التشغيل | `apps/api/src/modules/ops/opsRepository.ts` | upsert/قراءة النبض، عمق الطابور وعمر أقدم جزء، نوافذ التسليم والمحاولات، لقطة الالتقاط. |
| خدمة التشغيل | `ops/opsService.ts` | `readiness()`، `metrics()`، `heartbeat()`، ثابت `PUBLISH_WORKER`، وحالات `ok`/`stale`/`missing`. |
| المسارات | `ops/opsRoutes.ts` | `createPublicOpsRouter` (`/healthz`, `/readyz`) و`createAdminOpsRouter` (`/api/v1/admin/metrics`، مدير فقط). المسار العام يُركَّب **قبل** `attachSession` فلا يتطلب جلسة ولا CSRF. |
| ربط العامل | `publishing/deliveryWorker.ts`, `publishing/runtime.ts`, `telegram/runtime.ts` | `heartbeat?` يُنادى في كل دورة داخل `try/catch`: فشل النبض **لا يُسقط** دورة إرسال. النسخة `worker-<pid>` ونبضها يُسجَّل عبر `PublishingRuntime`. |
| المهاجرات | `0018_dashboard_read_indexes.sql`, `0019_ops_heartbeats.sql` | فهارس قراءة (`0018`) وجدول `worker_heartbeats` بمفتاح مركّب (`0019`). مطبَّقتان على قاعدة التطوير. |
| الإعداد | `src/config/env.ts`, `.env.example:86` | `TG_OPS_WORKER_STALE_SECONDS` (افتراضي 120، المدى 30–3600). |

**عقد الجهوزية:** `503` فقط عند تعطّل قاعدة البيانات (فحص `select 1` بزمن قياس).
عامل متوقف أو غائب يُبلَّغ عنه بـ`state: 'stale' | 'missing'` **دون** إسقاط الجهوزية —
لأن تعطّل النشر ليس تعطّل الواجهة، والقرار يبقى مرئياً في `/readyz` وفي المقاييس.

**الخصوصية:** لا كلمة `token` ولا نص رسالة ولا رقم تواصل في أي استجابة أو سجل؛ مؤكَّدة باختبارات
تفتيش على النص الخام للاستجابات (D07/O03/Q24). لوحة المدير أعداد مجمّعة فقط، بلا أي مسار إلى محتوى مستخدم.

## 4) ملاحظات صادقة

- عدّاد الفلاتر **صفر** لمستخدم جديد: بذور النظام تُنشأ عند أول استخدام لمحرك الفلترة (تسجيل كسول)
  لا عند التسجيل. هذا سلوك قائم من مرحلة سابقة، ووثّقته في الاختبار بدل تغييره.
- ذاكرة اللوحة في العملية الواحدة؛ مع عامل واحد (Q27) هذا كافٍ، وأي توسّع لاحقاً يحتاج Redis أو إسقاطها.
- `0019` تُبقي صفاً واحداً لكل (اسم، نسخة) فلا ينمو الجدول تاريخياً — احتفاظ بالتصميم لا بحذف دوري.

## 5) ما لم يبدأ (بانتظار إشارتك)

P4‑ج صفحة السجلات والأخطاء، P4‑د الاحتفاظ/الحذف/الإعدادات (`0020`–`0021`)، P4‑هـ اختبار الفلتر
+ الترقيم المؤشِّر + رحلة العمل + إعادة نشر الفاشل (`0022`), P4‑و مركز الإشعارات + رحلة E2E (`0023`),
P4‑ز جاهزية الإنتاج. وتعديل/حذف الرسائل المنشورة (§20/17–18) يبقى **خارج V1** كما اتُّفق.
